# B1 — バックエンド起動の有限検査と空判定の診断

ソースカーネル候補の間欠的メモリ異常は未解決です。過去の添付試験で、全0の2GiBディスクなのにメモリ警告/検査SIGSEGVを非空ディスクと表示しました。書式化はされていません。原因をホスト/ハード/Python/カーネルへ断定せず、失敗証拠も保持します。診断と有限の実VM証拠を増やす段階で、カーネル合格とはしません。

一定メモリの全走査と終了0だけ書式化を維持します。検査CLIはブロック装置と全0を確認した時のみ0、非0データ検出のみ2、不正装置/stat/read失敗は3。予期しない終了/信号も実行失敗とします。initはset-e下で結果を取得し、2を既存nonblank-state-disk、他の非0をstate-blank-check-failedへ分け、mkfs前に停止します。既存ext4・mount・DB待機・bootstrap/秘密・ユーザー・権限・隔離を維持します。単体試験では判定部分だけを偽python/mkfsで実行し、ホストで実init/実書式化はしません。CLI装置判定は標本ファイル用モック、全走査読み取り試験は維持します。

VMProbe --backend-preflight artifacts NEW_PRIVATE_OUTPUTは1起動だけです。出力の既存ディレクトリを原子的に拒否し、アプリ/ブラウザ/ユーザーディスクを触りません。専用0700領域に2GiBスパースディスクを作り、検証済み成果物/資格情報生成を再利用し、120秒で待機します。隔離4行と秘密の非出力を確認し、GET auth/statusと保護プロフィールのみ取得、未初期化/401を要求して正常停止します。初期設定/プロフィール変更/タスク/エージェント/クラウド/共有/NICは追加しません。失敗時は所有VMを1回強制停止し、固定の真偽/数値/列挙分類だけを出力します。生エラー/ログ/トークン/パスは公開せず、ローカルの秘密領域に保持します。既存完全バックエンド試験の既定挙動は変更しません。

Coreの正規化結果はハードウェアなしで試験できます。書式化ステージの観測を含め、PASSはready/認証/隔離/秘密非出力/正常停止/VM解放/異常なしをすべて要求します。非空と検査失敗を分け、過去の信号+非空表示は両方記録します。観測の分類であり、原因やログだけのディスク完全性保証ではありません。秘密値は結果型に入りません。

実行前にプロセスとハッシュを確認し、未変更ソース候補を新規状態で最大1回だけ試験します。結果を残し、修正initを別のオフラインLinuxビルド/候補へ組み込み、既定/旧成果物やブラウザを置換しません。固定パッケージと同一カーネルで新候補も1回のみ試験し、成功まで繰り返したり成功だけで昇格/安定性合格にしません。ビルドのみDockerを許容し、CLI実行では使いません。ハッシュ/手順/正規化結果と秘密ローカル位置を分離します。進められない場合も証拠を保持し、他の承認済み作業を続けます。

要件→設計→RED/GREEN→レビュー→全体回帰→署名/ビルド→実VM制御試験と日英記録です。UI変更がなくLazyweb対象外です。新しいゲスト失敗名は既存の汎用VMController失敗処理を通し、UI文言を追加しません。反復起動/復旧、実ネイティブ/ブラウザ操作、全21機能、ネイティブクラウド通信、配布は未完了です。

全ログ証拠の修正：controller.guestLogは表示用64KiB末尾のみです。所有VM停止後に、上限8MiBの完全な単一ログで異常/隔離行/プロビジョニング秘密の非出力を同時に検査します。不正/欠落/複数/過大/変更中なら取得不可として合格にしません。結果型は表示末尾ではなく正規化済み完全監査を受け取ります。初期メモリ/信号異常の後に100KiBの正常出力が続いても、他のready/API/停止条件が揃っていても失敗とする試験を加えます。認識した異常がログにないという証拠であり、カーネル安定性の保証ではありません。

### 静的ディスク検査候補の再ビルド

開発者向けのLinux ARM64ビルドです。確認済みのCloud Preview成果物と、ローカルDocker Desktopに保存済みの固定ランタイム・コンパイライメージが必要です。検査プログラムと10ケースの単体試験はコンテナ内でコンパイルします。ビルドコマンドは対照版をハッシュで検証し、再構築したディスクを抽出します。検査バイナリは以前の実験と同じハッシュを要求し、新規の専用ディレクトリに診断用マニフェストを生成します。通常版のパッケージ作成には確認済みのCloud Previewマニフェストが引き続き必要です。

```sh
python3 script/build_static_blank_checker.py \
  --control 'dist/NetworkPNTR Mac Cloud Preview.app/Contents/Resources/Guest' \
  --output .build-cache/new-static-checker-guest
```

検査バイナリは以前の実験と同じバイト列で再構築できます。イメージやext4全体にはビルド日時・ファイルシステムのメタデータが入るため、別ハッシュになることがあります。署名済みVMProbeの `--backend-preflight` に候補と未使用の診断出力先を渡すと、新規ディスクと隔離VMで起動を確認できます。[最新の起動記録](bugs/guest-boot-investigation.ja.md)

### システムディスクのキャッシュ方式を切り分ける

Debug版のVMProbeは、同じゲストで `cached` と `uncached` を明示して比較できます。設定はAppleの[ディスクイメージ接続API](https://developer.apple.com/documentation/virtualization/vzdiskimagecachingmode)を使います。変更するのはシステムディスクのキャッシュだけで、読み取り専用と完全同期は維持します。書き込み可能な状態ディスクには従来どおりの接続を用い、各回で新しい専用ファイルを使います。既存の読み取り専用APIと隔離を検査し、クラウド通信を有効にした起動とReleaseビルドでは診断用の上書きを拒否します。

```sh
VMProbe --system-disk-cache-preflight uncached /path/to/verified/guest /path/to/new-private-output
```

回数と順序を固定して比較します。停止後のログを監査し、成功・失敗ともに残します。単発の正常起動だけでキャッシュ方式が過去の障害を解決したとは判断しません。

### アプリ画面で検出済みのカーネル障害を保持

既存のパニックとOopsのログマーカーを、ゲストのカーネル障害として分類します。同じVMで後続のログ読み取りや停止エラーが発生しても、検出済みのカーネル障害を保持し、新しい起動の開始時に解除します。接続失敗画面と実行環境に同じ日英メッセージを表示し、既存の実行環境への移動・停止・再試行の操作を使います。説明の近くに次の操作を置く構成は、LazywebのRarible初期化エラーの参考例を取り入れました。表示するのは検出した障害の種類です。

## Attachment transport implementation boundary

Inspection of the pinned server/chatupload.go confirms that128MiB bounds the multipart body, including boundaries/part headers, rather than each file. ParseMultipartForm uses32MiB memory before spilling; duplicate names receive suffixes instead of overwriting. Session upload uses id=conv-<positive conversation ID>. The server response contains guest abs paths; native presentation must not confuse those with Mac paths or offer a host-open action.

Keep BackendJSONTransport/BackendHTTPRequest and their4MiB request/response checks unchanged. Add a separate authenticated multipart capability through AuthenticationSession so401 still clears the session and Keychain. Do not expose bearer values to ChatWorkspace or the file picker. The new runtime API owns one VZ connection and a duplicated descriptor per transfer. A cancellation handler must actively interrupt the duplicate and terminate the worker, including while polling or stalled in a write; cancelling a detached Task alone is insufficient. VM stop invalidates transfer identities. Responses remain finite/bounded JSON and are parsed with existing status/framing validation. The guest relay already uses64KiB buffers and a fixed loopback endpoint; no host shares, NIC or general file RPC is required.

Represent multipart framing and checked total length before connecting. Read selected regular files in bounded chunks, never concatenate128MiB into Data or increase the generic JSON cap. Explicitly selected files are scoped to the transfer and released on success/error/cancellation. Validate selected-file identity/size and observed metadata before/after reading, reject short/extra reads and changed observations, and document that this is not a filesystem snapshot guarantee against concurrent same-metadata mutation. If stable retries need a snapshot, use an app-private bounded staging copy, not a shared directory. Only basename and content travel; no Mac absolute paths, bookmarks or security-scope tokens enter request metadata. Filename escaping and empty/duplicate/Unicode file behavior require actual pinned-browser multipart comparison, not an assumed browser implementation.

Implement in ordered gates: A1 pure multipart framing/length/file-read regression tests, including exact body limit and over-limit rejection before any socket; A2 real socketpair backpressure/partial-write/cancel/early-response/timeout tests and authenticated session handling; A3 signed app/VM uploads with content hashes, zero-length/repeated names and128MiB-body boundaries compared with the disposable reference; A4 keyed draft attachment ownership, create-on-selection handoff, attachment-only send, failed-send restoration, removal without deleting guest data, conversation switch and VM-stop tests; A5 native picker/cards/progress/error controls and external browser/native keyboard/accessibility/visual pairs. Obtain current Lazyweb evidence before A5 UI work. A1-A3 are backend/transport work, so Lazyweb is outside their scope. Original browser ingress currently caps uploads at64MiB; large-body backend comparisons must use a dedicated disposable reference with a matching128MiB-or-higher ingress cap, or an explicitly recorded direct internal backend route. Do not silently change the user's8787 deployment or mistake its ingress rejection for the pinned ARTEX limit.

This is a design checkpoint, not an implemented upload path or attachment parity claim. The pending citation viewport/Undo external retests remain required independently.


A1 implementation detail: ChatMultipartBody is a single-consumer synchronous reader created/consumed by the future transfer worker. It preflights regular selected file URLs, framing and checked Int64 body length; keeps metadata per file but opens at most one content descriptor during reading. Each reopen is compared by device/inode/size/mtime/ctime against preflight; reading uses at most64KiB per call. A descriptor is checked before chunks and at EOF, closed on completion/failure/cancel/deinit. Public close marks cancellation; failed readers are terminal. This observes ordinary replacement/truncation/growth without claiming a snapshot. Empty selection, non-file URLs, directories/FIFOs, invalid boundary and oversized body fail before any connection. Tests include exact128MiB using a sparse temporary file, independent multipart wire expectations, escaped filenames, chunking and cancellation. ## A3 bounded full-content verification

Use a single GET of the pinned workspace/download handler (server/workspace.go calls http.ServeFile), not multiple Range requests that might mix file versions. Consume at most64KiB per feed and hash incrementally with CryptoKit SHA256. Success requires HTTP200, one decimal Content-Length equal to the expected attachment metadata, no Transfer-Encoding or nonidentity Content-Encoding, and at most128MiB. Header storage is64KiB; no full success body is retained. Finite error responses are at most4MiB and report status through the authenticated revision guard, never body text or tokens. Reject malformed/duplicate framing, unexpected status206, missing success length, truncation and extra bytes. A single response is not a guest filesystem snapshot; don't claim detection of same-size concurrent mutation. Expected synthetic SHA independently proves the controlled fixture's bytes.

First implement/tests the incremental digest state machine (split headers, every binary byte, empty/exact/over bounds, malformed framing and terminal failures). Then implement a dedicated nonblocking socket exchange with owned cancellation/finite deadline and backpressure/short-read tests. Integrate a typed authenticated attachment-only capability (positive conversation ID, single safe basename, expected size) and runtime post-await lease checks before diagnostics. Extend independent disposable reference hashing and compare actual large-file hashes. Existing upload/JSON paths remain bounded. No NIC, host share, host command endpoint or UI change is introduced; Lazyweb is outside this backend work.

## Attachment transfer progress and live cancellation

Pinned chat/page.tsx uses uploading state to show a spinner and disable attachment/send controls; it does not provide a byte-percentage parity oracle. Native numeric progress is transport evidence pending later UI design/comparison. Add an optional Sendable synchronous nonblocking progress callback with immutable sentBodyBytes/totalBodyBytes. Values count successful writes of the multipart body only, never preamble or HTTP headers. Emit first positive progress, then at most once per50ms, plus final body completion; do not queue per-chunk MainActor Tasks in transport. Callback delivery occurs on the worker and cannot imply server acceptance. Consumer UI ownership/generation checks remain required when scheduling main-actor updates.

Authentication owns a locked delivery gate for each progressing upload. Invalidate gates on revision changes and when the request returns/throws; stale callbacks cannot be newly delivered after invalidation. Reuse tracked socket cancellation, post-worker lease and explicit post-await Task cancellation before accepting upload replies. Callbacks must be short and must not synchronously wait for the main actor; cancellation from the callback remains supported without a gate-lock reentry deadlock.

Ordered tests: clock-controlled rate/monotonic accounting and invalid input; actual socket callback cancellation before full body; session callback lifetime and uncooperative cancelled reply; fresh signed native VM with128MiB-body fixtures, cancel task on first body progress and assert partial bytes/no success/VM still usable, then stop VM during another in-flight transfer, restart and authenticate/clean only owned conversation/files. Separate test-owned progress signaling must never become a host command RPC. Native diagnostics success artifacts require all cases and cleanup. No UI change in this stage; Lazyweb is outside scope. Mid-stop observation must record actual partial progress rather than infer interruption from a stopped VM.

Strengthened interruption witness after review: signal only after at least1MiB body progress, record task completion before delivering its result, and reject an already-completed operation before intervention. VMController captures the count of open, not-already-cancelled owned transfer sockets atomically when stop calls cancel; capture it before restart resets the count and require exactly one. Stop result must be CancellationError, not an arbitrary preceding network failure. This proves an interrupted owned transfer lease with partial progress, not a claim about every possible concurrent server failure or kernel stability.

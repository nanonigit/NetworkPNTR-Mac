# Requirements and completion goal

Build a native macOS ARTEX application, a separate private repository `nanonigit/artex-mac`. On this Apple Silicon Mac, launch, operate, stop, update and recover ARTEX without browser, Docker Desktop, terminal commands or a manually started server. SwiftUI owns the user interface; autonomous shell execution and PostgreSQL run only in an app-managed Linux VM.

## Release acceptance criteria

R1. All 21 upstream navigation features, every page/detail route and their controls are accounted for in feature-map.json; no functional omission is silently accepted. Final release requires equivalent workflows, not just similar-looking screens.
R2. Browser commit e75ae371ad777ffd1eecdd28d2781a6519b05591 is the reference. Compare identical fixtures, validation, errors, empty states, progress/SSE, cancellation, mutations, exports and persistence. Each case has separate automated/API and human-observed UI evidence.
R3. Native sidebar preserves Features/System hierarchy, wording, ordering and task/detail relationships. Native menus, keyboard access and window behavior may improve ergonomics; differences require a documented reason and parity case. Use Lazyweb as secondary evidence; upstream is authoritative.
R4. No host shell execution by agents, no Docker socket, no shared host directories, no arbitrary host RPC. Guest networking is off initially. Later grant explicit egress/target policies; cloud credentials never appear in logs or Git.
R5. Start/stop/restart, failure, crash, disk-full and update rollback are tested. Persist data on a guest-owned disk. Existing browser installation remains a separate preserved reference; migrate only via a tested explicit import.
R6. Package a locally runnable .app; production signing, notarization, clean-Mac install, licenses and verified restore are final-phase gates. Phase 1 supports Apple Silicon only, macOS 15+; Intel support is not claimed.
R7. No fake task/LLM results or phase-completion claims. Distinguish lifecycle state, guest-ready evidence and API readiness. A new server response does not prove a native workflow works.

The current authorized first milestone is Phase 0 documentation and Phase 1 executable VM proof. Later phases remain required by the full goal, and cannot be marked complete by a mock UI or browser wrapper.

A3 content-verification extension: hash every byte of the actual near128MiB attachment through authenticated vsock using bounded memory. Preserve generic JSON4MiB limits, session revision isolation, cancellation/VM-stop descriptor ownership and the fixed browser. One successful response must have the expected metadata size and exact HTTP framing; incomplete/oversized/encoded/ambiguous responses fail. This proves received bytes, not a filesystem snapshot under concurrent guest writes. Full native attachment UI and download/export workflows remain separate acceptance gates.

Attachment progress/cancellation extension: report monotonically increasing multipart-body bytes actually written, excluding credentials/HTTP headers/host paths. Bound delivery rate and keep the final body-written event distinct from server acceptance. A cancelled task, VM stop, logout or superseding login must not revive a transfer or accept its obsolete result. Verify real signed-VZ mid-transfer cancellation and stop separately from socket/unit tests; preserve browser fixtures and cleanup owned partial uploads after restart.

A4 attachment draft requirements: preserve returned name/path/size, discard optional guest abs from native send/presentation, validate a single uploads/basename with bounded nonnegative size. Attachment-only messages must reach the existing send route, while empty text plus no attachments fails before transport. Per-conversation attachments must not cross selection/reset lifetimes. Match browser optimistic send clearing and failed-send restoration, preserving newer edits and newly added attachments. Removing a card changes local draft only, never deletes guest data. Stop restores unconfirmed optimistic submissions; reset clears all. Conversation creation/upload handoff and picker/cards remain required subsequent gates.

A4.2 upload ownership: feature code uses an authenticated typed attachment capability with no caller bearer. Empty selection/unsupported capability fails before creating a conversation. New-draft selection creates once and uploads to that new positive ID; existing selection uploads directly. Preserve the original/newer draft text and returned metadata during handoff. A selection change may cache results for the original owner but cannot steal selection. Support one operation per origin/target, explicit cancellation, stop/reset and confirmed-deletion invalidation; stale results/progress cannot affect a newer operation. Failed deletion preserves existing draft data. Never delete already accepted guest files merely because a local task was cancelled. UI controls and complete end-to-end acceptance remain later gates.


When sending a chat draft, use the pinned browser ECMAScript trim semantics for the empty guard, wire message and failed-send restoration. Preserve newer draft revisions and attachment-only sends. Service calls preserve their supplied message bytes; their empty guard uses the same whitespace set. UI gating is a separate A5 gate.


A5 attachment UI: use a window-owned native multiple-file panel, excluding directories/packages; cancellation creates no conversation. Show uploaded relative filename, byte size, local-only removal, upload progress and visible safe error. Keep file access scopes for the transfer lifetime and release on success/error/cancel; leaving the screen cancels owned tasks/panel. A stale panel completion cannot upload into a different conversation. Allow attachment-only send with shared ECMAScript whitespace; disable send while busy/loading/uploading/running. Compare actual native interactions with the pinned browser using synthetic disposable files and no provider credentials.


A6 persisted user messages: display full plain text and read-only attachment name/relative path/size cards from inline or lazily fetched Detail JSON {text, attachments}, matching pinned UserRow. Load only mounted user rows, preserve summary on empty/error replies and show a safe retryable failure. A cancelled, disappeared, updated or different-conversation row cannot accept an old detail response. Keep validated metadata and ignore abs; malformed unsafe attachment records fall back to literal body text. No file open/delete/download or host RPC is introduced. Compare structured/plain/empty/error/Unicode fixtures against pinned source and actual browser/native rows.

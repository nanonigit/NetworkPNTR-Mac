# 外向き通信のオフライン証明書検証

直接接続ワーカーは、数値IPに固定したPOSIXソケットを使い、SecureTransportのハンドシェイクをサーバー認証で一時停止する。固定ホスト名とチェーンを、証明書・失効情報の外部取得を無効にして検証する。証明書検証、ハンドシェイク、実ソケットの照合をすべて通過してからHTTP要求を送る。Swift側の要求、キャンセル、ストリーミングの呼び出し方法は従来どおり。使用したシステムAPIは非推奨で、TLS 1.2までをサポートする。[AppleのSecureTransport資料](https://developer.apple.com/documentation/security/secure-transport)

隔離試験では、別のループバックソケットを発行者・OCSP・CRLの取得先として証明書に記載した。中間証明書を省いた場合はHTTP要求の送信前に拒否し、同じ証明書で中間証明書を添えると接続できた。どちらの場合も監視ソケットへの接続は0件だった。ホスト名不一致、未信頼チェーン、TLS待ち、キャンセルとタイムアウト、プロキシ拒否、応答の切断・上限、送信待ちが生じる8 MiBの本文の一致も確認した。TLSのソケット処理中もキャンセルと期限を確認し、その結果を呼び出し元まで返す。

Mac上では、同じIP固定とオフライン検証の処理でOpenAI・Anthropic・Gemini・GroqへのTLS接続を試験した。診断は同じDNS検査を使い、TLSの後に実ソケットの宛先も照合する。ソースと実行ログは `.build-cache/cloud-egress-offline-trust` にある。診断でのHTTP要求と認証情報の送信は0件。5秒上限の試行では13件すべてが時間切れになった。8秒上限で再試行すると13件すべてで接続先と証明書を確認できた。[検証記録](../evidence/llm/cloud-egress-offline-trust-verification.json)

次は、HTTP応答のフレーミングと、VMの起動停止に連動する専用vsockを実装する。署名済みVMの隔離、4社への実API要求、固定ブラウザ版との操作比較は後続の受入条件。ホストCIは未検証。

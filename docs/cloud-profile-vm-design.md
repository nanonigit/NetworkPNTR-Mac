# Isolated cloud profile persistence

Use the compiled cloud1 backend in a fresh CPU1 source-kernel candidate. The build inherits the verified loopback-only system image and init, checks the input binary/init SHA-256 before rebuilding the read-only system disk, and reuses the verified kernel and initramfs. The candidate has zero NICs and host shares. A DEBUG-only probe requires the pinned backend digest and version, validates artifact integrity through VMController and checks the live health version. This phase exercises the existing PostgreSQL profile API with the actual Swift LLMService and production preset initializers.

Use a new mode-0700 result directory and a blank 2 GiB state disk. Boot once, check the unauthenticated API rejection, set up a disposable admin, create exactly four inactive/excluded profiles with independent synthetic keys, validate canonical URL/format, decode masked hints and edit Gemini with a blank key. Reload the same persisted disk after cooperative stop, generate new transport credentials, login using the same admin password and verify the original IDs, field values and masked hints. Read the conversation and LLM record counts at both boots. Stop and audit each boot's isolation and credential absence. Require the format witness only on first boot. The report contains safe profile metadata and verdicts, without raw responses, hints or secrets.

Validate the candidate and profile snapshot against wrong digest/version, network/share/CPU changes, wrong URL, missing hint and duplicate/extra rows in focused tests. Release builds reject the diagnostic mode. A successful profile round trip closes actual profile storage evidence for CP1b. The next CP2 runtime gate covers tool transcript persistence and replay across reboot. Live cloud egress, UI and browser comparisons, kernel/default promotion and release remain distinct acceptance conditions.

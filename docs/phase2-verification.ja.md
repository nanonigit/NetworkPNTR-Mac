- Python 10テスト：認証フレームのサイズ制限と拒否、途中切断、大容量の双方向通信と片側終了、ディスク全体の読み取り専用検査、カーネル追加モジュール、既存の起動形式。
- 実VM内で、固定したARTEXとPostgreSQL 16が起動。OSディスクは読み取り専用、保存用は専用ディスク。NIC・ホスト共有はゼロ。
- 認証付きvsock経由のHTTPに成功。通信トークン不正は切断、未ログインの保護APIは401、初期設定トークン不正は403。初期設定と非ストリーミングのLLM設定の保存・読み取りに成功。
- 通常再起動・強制停止後の再起動で、パスワード・JWT・設定レコードを保持。不正な既存ディスクはエラーを表示し、フォーマットせず検査領域も保持。
- 固定ブラウザ版を使う別の使い捨て環境と、同じ操作のAPI結果が一致。比較は5つのバックエンド条件に限ります。243 API全体や画面・操作感の同等性は未合格です。既存のブラウザ版DBは変更していません。
- 起動用の秘密値がゲストのコンソールログに出ないことを確認。イメージ・状態・生ログはGit対象外。公開する証跡は資格情報を含まないJSONと合格記録だけです。

再現コマンド：`script/test_backend.sh /path/to/pinned/artex-global`。開発時のイメージ構築と比較環境にはDockerを使います。VM検証プログラム自体はDockerを呼びません。現時点の開発用構築は、固定ダイジェストのローカルブラウザ版イメージを再利用し、ARM64とソース識別情報を確認します。他のMacでもソースから再現できる配布用ビルダーは、今後の配布条件です。

## 不具合の経緯・原因・対策

1. OSディスクをマウントできなかった原因は、初期イメージ内の `/sbin/modprobe` が欠け、ext4がCRC32Cを自動ロードできなかったことです。入口を追加し、パッケージ形式の回帰テストと実VMで検証しました。
2. BusyBoxの `blkid` にutil-linuxのオプション仕様を仮定していました。実出力からext4を確認し、異なる場合は全領域を検査します。空ではない不明なディスクは拒否します。
3. 当初の `head`・`cmp` による空ディスク検査中、`head` の終了処理でゲストカーネルのメモリ異常が再現しました。カーネル自体の根本解決とはしていません。1 MiBずつ読み取る方式へ変更し、末尾の非ゼロ検出と実VMの初期化成功を確認しました。この変更だけでカーネル全般の信頼性を保証するものではありません。
4. ルート切替後の標準入力を使う `stty` が失敗しました。`/dev/hvc0` を明示し、失敗時は秘密値を送る前に停止します。秘密値をエコーせず起動することを検証しました。
5. 初期化処理の異常終了によるパニック・再起動ループを防ぐため、明示的なエラー状態で待機し、`panic=0` とカーネル異常検出を使います。準備完了後もコンソールの異常を監視します。

観測した時系列と因果関係を記録し、修正と回帰検証を行いました。AIエージェントをホスト上で動かす経路は追加していません。テスト用の状態ディスクはGit対象外の `evidence/local` に残ります。整理する場合はテスト用と確認したディスクだけを削除し、利用者の保存ディスクを削除しないでください。

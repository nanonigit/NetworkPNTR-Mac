# Saved provider credential target verification

The real model discovery, connection test and profile save handlers used synthetic credentials in isolated PostgreSQL 16. Before the change, requests reused a saved key after changing the base path, wire format or proxy. The global fallback also sent out-of-scope requests, and a blank-key save moved the existing key to an edited path.

The fixed handlers reuse stored keys for matching targets and accept explicit keys for edited targets. A concurrency test observed a real PostgreSQL row lock. Once a new key and URL committed together, the waiting blank-key edit was rejected and the replacement pair remained intact. Discovery with a saved key uses the completion client's base path and defaults. Additional cases check parent-path fallback, a suffix from another wire format and preservation of an environment override's trailing slash.

The Linux/arm64 builder used the pinned browser source, checked managed patches and a verified module cache. PostgreSQL and the focused test shared a disposable loopback-only namespace with the database files on tmpfs. To reproduce, follow the [redirect verification build](cloud-redirect-verification.md) with the provider-test Dockerfile from commit `f01c76a`, the current `origin-extension` and `provider-credential-target.patch` in the context root. Set `ARTEX_CREDENTIAL_TEST_DSN` to the disposable PostgreSQL service and run `go test ./server -run '^TestManagedCloudCredentialTarget$'`. The [verification receipt](../evidence/llm/cloud-credential-target-verification.json) records test counts and the image, patch and binary digests.

The build is a managed backend candidate. Default guest promotion, VM egress, live API checks for all four providers and Mac/browser workflow comparison remain open. Lazyweb is outside this backend phase. Hosted CI remains unverified.

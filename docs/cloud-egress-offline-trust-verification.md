# Offline certificate validation for cloud egress

The direct worker uses a pinned POSIX socket and pauses SecureTransport before server authentication. It evaluates the fixed hostname with certificate fetching disabled and a network-disabled revocation policy. The worker sends no HTTP bytes until the certificate check, TLS handshake and peer check succeed. Swift's request, cancellation and streaming interfaces are unchanged. The current system API is deprecated and limited to TLS 1.2. [Apple SecureTransport documentation](https://developer.apple.com/documentation/security/secure-transport)

An isolated certificate fixture advertises issuer, OCSP and CRL endpoints on a separate monitored loopback socket. The missing-intermediate handshake is refused before any HTTP bytes. The same leaf succeeds when the server supplies the intermediate. The monitoring socket receives zero connections in both cases. Other loopback cases cover mismatched and untrusted certificates, a held handshake, cancellation and timeout, proxy denial, truncation, response limits and an exact 8 MiB write with backpressure. Callback guards latch the active phase's cancellation or deadline before TLS socket I/O and preserve that result through the TLS call.

A handshake-only diagnostic exercised the exact pinned socket and offline trust functions against OpenAI, Anthropic, Gemini and Groq on the Mac. The diagnostic uses the same DNS admission code and checks the peer again after TLS. Its sources and logs are under `.build-cache/cloud-egress-offline-trust`. It sent no HTTP requests or credentials. A five-second run timed out for all 13 candidates. A follow-up with an eight-second budget verified all 13. See the [receipt](../evidence/llm/cloud-egress-offline-trust-verification.json).

The next integration gate is the bounded HTTP response stream and the dedicated guest-to-host vsock service tied to the VM lifecycle. Signed VM isolation, live provider requests and comparison with the frozen browser remain open. Hosted CI remains unverified.

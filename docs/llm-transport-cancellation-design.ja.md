# LLM通信の取消チェックポイント

## 要件

取消済みのLLM処理は送信しない。取消を無視して返る通信実装でも、取消後の応答を現在の成功として返さない。既存の有限JSON上限4 MiBを要求・応答に適用する。固定版e75ae371ad777ffd1eecdd28d2781a6519b05591の経路・メソッド・部分更新・有効プロファイル削除禁止・ID・応答契約は維持する。実際のキーやクラウド通信は試験に使用しない。

## 設計

11系統の要求が共有するLLMService.rawに、送信直前とawait直後の取消確認、バイト上限確認を置く。空のローテーション更新は無操作のままとし、ちょうど4 MiBは許容する。今回は通信境界の修正であり、ストアの所有権や書込結果不明時の復旧は未完了。送信済みの書込は取消時点ですでに成立している可能性がある。自動再送は追加しない。結果確認・明示的再開とエディタのライフサイクル管理は次の課題。UIを変更しないためLazywebは対象外。

## 実装・検証順序

1. RED：11系統の送信前取消、通信応答時の取消、要求・応答の上限超過と上限ちょうどを試験する。
2. GREEN：公開APIと通信契約を維持して共有境界を修正する。
3. レビュー、関連・全体回帰、カバレッジ、署名付きビルド、CIを確認する。実画面比較は手動ロック解除後とし、合成試験を実際のゲスト比較とは扱わない。

# Tasks T2 — state and lifecycle

Scope: a native observable TaskStore on the main actor, using T1 TaskService. No screen change or feature-status promotion. Fixed browser source remains e75ae371ad777ffd1eecdd28d2781a6519b05591. Its task list polls every10seconds, keeps previous data on read failures and refreshes after changes. Native state additionally exposes safe localized errors/staleness. Opening detail is a read; never POST /api/active. No live user backend or host AI execution in tests. Lazyweb is out of scope for backend state only.

List and detail expose value/loading/failure/stale. Selected ID is canonical; switching selection clears old detail immediately, advances a selection ticket and suppresses old responses. Repeated selection of the same canonical ID can refresh without discarding a known value. Reads use independent UUID tickets; begin mutation/stop/reset invalidates old reads and clears loading flags. Refresh failures retain known values, visibly stale; cancellation does not become a communication error. No overlapping same-state read; newer tickets cannot be cleared by older defers.

One per-store mutation gate serializes create/metadata/control/batch/delete. Mutations may supersede in-flight reads. Every dispatch is once: no implicit mutation retry. Outcomes distinguish notStarted(busy or already cancelled), rejected(typed local input, no send), confirmed(valid T1 result), unconfirmed(other errors/cancellation after starting), discarded(auth/reset generation changed). Only the current authenticated lifetime may retain results/errors. Keep operation confirmation separate from read failures; confirmed mutation returns confirmed even if follow-up refresh fails. Unknown outcome must be reconciled by UI/user, never treated as proof of rollback. Transport errors cannot reliably prove whether a request reached the server.

Store a typed last confirmation with target identity, sanitized mutation failure and uncertainty flag. A new explicit mutation clears prior notice only after acquiring the gate. Selection changes do not redirect an old operation's owner or implicitly select a newly created task. Confirmed deletion removes exactly its owner from current list, clears active/selection if matching, and never resurrects it through an earlier read. Other confirmations retain previous aggregate data as stale until a fresh list response: metadata/detail responses carry zero aggregate counters, so replacing list records would lose metrics. Batch partial results remain available for UI to explain each owner; no automatic retry of failed items.

Stop invalidates read/poll tickets but retains cached state and does not release a mutation gate before the actual operation terminates. A confirmed operation after stop remains recorded, but does not start background refreshes. Reset clears user data and changes the authenticated lifetime; outstanding mutations retain the gate until terminal and return discarded without exposing prior-session results. A store is owned by one window/authenticated session; future wiring must call reset on sign-out and hold that store through pending operations. This is not a cross-store or server idempotency guarantee.

Polling has one owner, reads immediately then sleeps10seconds, refreshes list and selected detail, checks owner/cancellation between awaits and cleans up only its own ticket. Inject sleep for deterministic tests; no timer-based race tests. Controlled delayed replies verify response reordering, mutation/read invalidation, stop/restart/reset, confirmed-refresh-failure, uncertain cancellation, duplicate-operation gating, all finite mutations and no activation. Browser/native runtime comparison, dialogs/drafts/filter/sort/selection UI, persistence, advanced task features and full21acceptance remain open.

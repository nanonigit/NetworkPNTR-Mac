# 高度なチャット：固定ソースに基づく実装計画

基準はe75ae371ad777ffd1eecdd28d2781a6519b05591。C4を進めますがC3/C5の未完了条件は残します。有限API/モデルはUI設計の範囲外です。UI接続前には既に閲覧したLazywebのチャット事例も参照します。

1. 引用：server/chat_mentions.go、db/chat_mentions.go、web/src/lib/chat-mentions.tsとcomponents/mention-textarea.tsxが根拠。9分類、20件ずつの不透明カーソル、前後空白を除いた200Unicodeスカラーの検索上限、2048バイトのカーソル上限。認証付きGET /api/chat/mentions?kind=&q=&cursor=で正確なInt64 IDと返却順を保持する。@[分類#id 名前]の中国語分類はブラウザと同じ通信形式で、画面の分類名とは分離する。括弧/JavaScript空白を正規化し、名前はUTF-16の100単位で切る。サロゲート境界はサーバーが復号する置換文字と整合させる。送信時にサーバーが実レコードを再取得し、ラベルで操作権限は増えない。テスト→有限サービス/トークン→デバウンス・キャンセル・古い検索無効化・ページ失敗/再試行・カーソル挿入/選択済み表示→データ入りブラウザ/Mac実操作比較の順に進める。
2. 添付：server/chatupload.goはmultipart要求全体128MiB。現在のネイティブJSON通信は4MiB・固定application/jsonなので、その上限を一律拡大して代用しない。独立したストリーミングmultipart経路、ファイル/全体サイズ、明示ファイル選択、ホストパス非送信、短い読取り/途中変更、キャンセル/VM停止、所有権を実装する。ブラウザは下書きのファイル選択時に会話を作成し、scope=session,id=conv-IDへ送信して本文/添付を引き継ぐ。添付だけの送信と失敗時の両方復元も必要。カード削除とVM内ファイル削除は同じではない。同名/空ファイル/上限前後/中断/引継ぎ失敗を比較する。
3. サイド質問：lib/side-questions.tsとserver/side_questions.goを根拠に親ごとの履歴/質問/クリア、安定したclient_request_id、キャンセル、SSE /api/side-questions/{requestID}/eventsを実装。UTF-8分割・逐次SSE解析・サイズ制限・再接続/履歴照合・キャンセルを先に用意する。/btw、モデル/文脈/スナップショット、再試行と状態も保持。模擬ストリームだけで実VM/参照/クラウドを合格にしない。

各機能はRED/GREEN→固定参照の正規化比較→署名付きアプリの実VM→同一データの両画面/異常操作→アクセシビリティ/IME/キーボード/クラウドの順に検証。独自の合格条件を満たすまで未完了とし、VM安定性・配布・残りの全機能も追跡します。

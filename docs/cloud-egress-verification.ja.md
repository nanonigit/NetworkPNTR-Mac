# 外向き通信ポリシーと直接TLS接続の検証

中継のポリシーは、OpenAI・Anthropic・Gemini・Groq向けに9種類の固定HTTP要求を生成する。ホスト名、経路、メソッド、認証、本文長、ストリーミング指定を試験した。ヘッダーに混入させる文字、上限を超える本文、空または混在したDNS応答、数値IP以外の接続先、IPv4とIPv6の特殊用途アドレスを拒否する。合成CAで署名したOpenAI名の証明書は、macOSの信頼検証で受理された。ホスト名不一致と未信頼の証明書は拒否された。リポジトリに含めた証明書は公開部分のみ。

初期のNetwork.framework診断では、直接接続を優先しても設定済みプロキシへ切り替わり得ることをレビューで確認した。その方式はアプリのコードから外した。別の診断ではmacOS付属のlibcurlでプロキシを無効にし、検査済みの数値IPに固定した。固定のHTTPSホスト名で証明書を照合し、`getpeername` で実ソケットのIPとポートも確認した。最終試行で4社に対するTLS接続13件が成立した。直接接続を失敗させた比較では、既定設定で監視用プロキシにCONNECTが1件届き、明示的にプロキシを無効にした場合は0件だった。診断で送ったのはTLS接続までで、HTTP要求とキーの送信は0件。

手元の再現用ファイルは `.build-cache/cloud-egress/direct` にある。`main.swift` がCoreのポリシーで検査済みの数値IPを列挙する。`probe.c` は `xcrun clang -Wall -Wextra -Werror -lcurl` でビルドし、TLS接続後の実ソケットを照合する。[検証記録](../evidence/llm/cloud-egress-verification.json)に、ソース、証明書、診断、試験結果のダイジェストを記録した。

今回確認したのはCoreの要求・アドレス検査と、Macからの直接TLS接続。VMのリスナー、本番のストリーミング中継、各社のHTTP応答、既定ゲストへの反映、Macアプリとブラウザ版の操作比較は後続の受入条件。画面変更を伴わないためLazywebは対象外。ホストCIは未検証。

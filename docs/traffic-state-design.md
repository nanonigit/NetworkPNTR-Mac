# Traffic window state and confirmations

TR2 implements state, not a screen or polling task. Keep the full Traffic scope in traffic-workflow-design.md and all original gates. This backend/state phase is outside Lazyweb UI work. Use TrafficService's fixed validated requests; extract internal prepare/execute so confirmation stores the actual immutable bytes before publication. Public apply remains compatible.

A window owns a query/owner/activity/session, last-good page/hosts/settings/detail reads and byte-identity ordered flow/host selections. Filters/pages keep cross-page selections and the selected exchange, matching the pinned page. Changed applied query rotates owner and invalidates read generations; failures retain last-good data marked stale. Only visible fresh rows/hosts can be newly selected. Query validation is synchronous and old read cleanup never clears newer loads. Page0-only polling eligibility is exposed, but no polling starts in this phase.

A confirmation UUID captures its owner/session/activity and validated immutable request. Matching-host scope includes only the host substring, never the other filters. Selected-host scope freezes the ordered exact strings; purge is its own operation. Capture settings remain separate from Traffic-page controls. Pending confirmation blocks editing/new reads and replacement dialogs; cancel has no transport. A consumed confirmation cannot replay. Actual dispatch callback is a logical invocation boundary, not proof of socket bytes.

One outstanding write gates changes. A post-dispatch error or departure records an uncertainty operation/revision. Reads never acknowledge it; a full fresh page+hosts+settings read begun under that same uncertainty revision/current owner is required before explicit acknowledgment. Wrong owner/revision or stale/failed/inflight reads cannot unlock writes. Stop/resume keeps uncertainty; session reset scrubs raw scope/read/selection data but retains a generic uncertain marker and any outstanding write until it settles. No durable process-restart uncertainty journal is claimed.

Lifecycle publication is guarded against synchronous Observation reentry. Accepted stop/reset requests revoke pre-dispatch tickets and drain after the current update; reset wins and repeated teardown is idempotent. Resume/configure/selection/confirmation cannot reenter mid-publication. Late read/write results have session/activity/owner checks; unknown errors never imply rollback or automatic retry. Confirmed deletion resets page0 and clears preview; selected-host/purge also clear host selection, while flow selection stays as in the browser. Confirmed capture updates only the known setting and invalidates catalog reads. All receipts still require subsequent real multi-host fixture comparison and UI acceptance.

Then review, scoped/full tests/coverage, local signed build. Traffic feature stays pending; no actual deletion/agent/host-network action is executed by these tests.

Verified boundary refinement: stop also resets the applied query, matching component unmount; login reset additionally scrubs the exposed unknown scope. Pending validated bytes stay private until an outstanding operation settles. Available index (not merely successful unavailable-sentinel decoding) is mandatory for recovery. Busy-release publication is part of ownership validation; a committed confirmed receipt followed by departure returns discarded to the retired caller without inventing a new unknown outcome. Gates are local to this store; no durable process/cross-window journal is delivered here.

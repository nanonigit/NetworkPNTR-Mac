# Cloud egress policy and direct TLS checkpoint

The broker policy generates nine fixed HTTP requests for OpenAI, Anthropic, Gemini and Groq. Tests verify the authority, route, method, authentication, framing and stream negotiation. They reject key injection, oversized payloads, empty or mixed DNS answers, named endpoints and IPv4 and IPv6 special-purpose ranges. An anchored synthetic certificate for the OpenAI name passes the same macOS trust policy that rejects the wrong name and an untrusted chain. The two checked-in fixtures contain public certificates only.

The initial Network.framework probe was exploratory. Review confirmed that a preference for direct connections can still fall back to a proxy, so the experimental connector was removed from the app code. A separate macOS system-libcurl diagnostic disabled proxies, pinned each vetted numeric address, validated the fixed HTTPS hostname and checked the connected peer address and port with `getpeername`. The final run completed 13 TLS handshakes across all four providers. In a controlled direct failure, the local proxy sentinel observed one CONNECT with libcurl's default settings and zero connections with proxies explicitly disabled. The diagnostic sent no HTTP requests or credentials.

The private reproducibility files are under `.build-cache/cloud-egress/direct`. `main.swift` enumerates the vetted numeric endpoints using the current Core policy. `probe.c` compiles with `xcrun clang -Wall -Wextra -Werror -lcurl` and uses connect-only TLS. It checks each authenticated socket peer before reporting success. The [verification receipt](../evidence/llm/cloud-egress-verification.json) binds source, fixtures, diagnostic and test results.

This checkpoint establishes request and address admission in Core and direct TLS feasibility on the Mac. The VM listener, production streaming transport, provider HTTP responses, default guest and native/browser workflow comparison remain acceptance gates. This phase has no product UI changes. Hosted CI remains unverified.

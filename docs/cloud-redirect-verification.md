# Provider HTTP redirect verification

The managed cloud3 client applies the same origin check to model discovery and chat completions. The comparison uses scheme, hostname and effective port. Same-origin redirects retain the request method, body and authentication for a 307. Other origins, URL user information and redirects past the existing hop limit are refused. The response keeps its HTTP status. Redirect bodies are discarded before provider capture, and rejected or malformed Location values are removed.

Two loopback servers reproduced the original failure without external networking. Go followed a 307 to another port on the same hostname and sent the synthetic bearer once in each of the discovery and completion paths. After the initial origin check, review identified a second exposure in the returned redirect body. Three tests reproduced the completion capture leak, the discovery error leak and the malformed Location error. With both controls applied, no cross-port request reached the destination. The tests also verified empty rejected redirect bodies, diagnostic redaction, preservation of a relative same-origin redirect and rejection of invalid origin or hop changes. The subsequent code review found no actionable defect in the tested change.

The offline Linux/arm64 build ran 594 passing Go test and subtest events, 116 existing skips and zero failures across the SDK, traffic, agent and server packages. Five passing tests covered the redirect changes. Guest artifact tests passed 183 cases. See the [verification receipt](../evidence/llm/cloud-redirect-verification.json) for the image, binary and input digests.

For reproduction, use the frozen source archive and prior overlays listed in [the cloud2 verification](cloud-indexed-execution-verification.md), with the provider-test Dockerfile from commit `7d44c0c`. Add `guest/backend-extension/cloud-origin` as `origin-extension` and copy `provider-origin-redirect.patch` to the context root. The offline run seeded only Go's module download cache from the verified cloud2 builder before `go mod download && go mod verify`, then applied the patches and ran tests and compilation without networking. The frozen browser checkout stayed clean at the recorded revision.

The tested scope is the managed HTTP client. The default guest still needs a promoted image. CP3 also requires a VM egress boundary, binding stored credentials to the intended endpoint before the initial request, and live acceptance against all four providers. This phase changes no product UI, so Lazyweb is outside its scope. Hosted CI remains unverified.

# ゲストカーネルのソースビルド：要件・設計・テスト

## 要件

K1. Docker.appのファイルを読まず、新しい開発環境でも候補カーネルを構築できること。Linuxソース・設定・コンパイラ環境・変更を固定し、使用前にハッシュを検証します。カーネルのコンパイルとソース側ビルドスクリプトはLinuxコンテナ内だけで実行します。アプリ実行時は引き続きVirtualization.frameworkを使い、NIC・ホスト共有・Docker呼び出しはゼロです。
K2. 現在動く診断構成を保持します。候補は読み取り専用ext4ルート、専用ext4保存、virtioコンソール・ブロック・乱数・認証付きvsockを組み込みドライバで使います。まず1 vCPUを明示して検証し、原因不明の2 CPU障害が直ったとは説明しません。
K3. ソース・設定・パッケージ・カーネルのハッシュ、コンパイラ、固定したビルド情報を出力します。上流ライセンスとソースアーカイブを配布時の確認用に残します。独立した再ビルドの一致前にバイト単位の再現性を主張せず、ビルド成功だけで配布・公証合格にはしません。
K4. 破損ダウンロード、パス・シンボリックリンク差し替え、異なるアーキテクチャ、必要ドライバ不足、構成ファイルの不一致を拒否します。ダウンロードと依存取得にはHTTPSを使えますが、コンパイル中はネットワークを無効にします。TLS検証を解除せず、実行用ゲストにDockerソケットやユーザーフォルダを共有しません。

## 今回の実験

Linux本流6.12.114を使います。kernel.orgのHTTPSチェックサムにあるアーカイブSHA256は 7a8589912bd7a8adb07fed074283652cf482a35facef8954554654f0154b4af3 です。既存Alpineゲストで固定した系列・版に合わせます。設定はLinuxKit f935f6b18cad69f08c1830b432d7dab90bf67614 のARM64設定（SHA256 53280e08ae286156a31049c90ab8b2077db93c0366a8a9e6bb4b3fa7c02f65fe）に、明示した変更を適用します。Docker Desktopの6.12.76を完全再現するものではなく、別の版・設定の実験です。過去の証跡と区別します。

LinuxKitの構築資料は https://github.com/linuxkit/linuxkit/blob/master/docs/kernels.md 、ソースのチェックサムは https://cdn.kernel.org/pub/linux/kernel/v6.x/sha256sums.asc です。HTTPS・ハッシュ検証を記録します。実行していないPGP署名検証を実施済みと説明しません。

Alpine 3.22.7のビルダーをdigestで固定し、パッケージ一覧を完全一致させます。ソース・設定はサイズとハッシュを検証してGit対象外キャッシュへ置き、macOS上では展開しません。最小限のビルド用ファイルだけをDockerへ送り、ホストのフォルダをマウントせず、並列数を制限してオフラインでコンパイルします。日時・ユーザー・ホスト・ビルド番号を固定し、Git由来の版番号を無効にします。モジュール読み込み・デバッグ情報を無効にし、必要なvsock・ブロック・ext4・コンソール・乱数を組み込みます。堅牢化設定を保持し、解決後の設定を確認してからビルドします。

カーネルとバックエンドの成果物は分離します。構成を組み立てる処理が両方を検証し、ソース情報付きの直接ルート・1 CPUマニフェストを生成します。既定のアプリ入力は勝手に置き換えません。実VM・実サービスのテスト後に採用を判断し、未解決の実行障害は配布品質の合格を妨げる条件として残します。

## テスト順序

1. Pythonテストを失敗させてから実装し、固定情報、サイズ・ハッシュ不一致、ARM64ヘッダ、解決済み設定、パス・リンク・成果物の整合性を検証します。
2. コンテナでビルドし、パッケージ・設定・ソース・ライセンス・ARM64 Imageと、コンパイル時の通信遮断を確認します。
3. 既存の検証済みシステムイメージを変えずに候補を組み立てます。署名したVMProbeで通常・強制復旧・不正ディスク保持、その後、新規アプリ環境で認証・LLM・ダッシュボードを検証します。既存のブラウザ比較結果と照合します。
4. コンパイルキャッシュなしで再ビルドし、ハッシュを比較します。新規ディスクの反復、停止・タイムアウト・起動キャンセル・実際の処理を検証します。1回の起動成功だけでは合格にしません。
5. ソース・ビルドの境界をレビューし、失敗と修正を日英で記録してpush・CIを確認します。ソース配布、バックエンドの新規ソース構築、最終安定性、製品・UIの全条件は別に証明するまで未完了です。

実行基盤の作業なのでLazywebは対象外です。ビルド前に空き容量を確認し、今回の追加使用量を8 GiB以内に抑えます。他のDockerイメージやユーザーデータを削除しません。

## 開発用コマンド（候補構成）

```sh
python3 script/prepare_kernel.py
python3 script/assemble_source_profile.py --backend guest/backend-artifacts --kernel guest/source-kernel-artifacts --output .build-cache/backend-source
ARTEX_MAC_GUEST_BUILD_DIR="$PWD/.build-cache/backend-source" script/build_and_run.sh --build-only
```

出力先は未作成の場所を指定します。毎回、新しい専用コンテナでコンパイルし、依存イメージの層と取得ファイルのみをキャッシュします。別の再ビルドには`--output .build-cache/kernel-source/rebuild2`を指定し、両方の完了後に`Image`と`kernel.config`のハッシュを比較します。この手順の記載だけで起動成功・再現性の合格とはしません。

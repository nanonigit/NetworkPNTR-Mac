# T13 アーカイブ Core 設計

固定 e75ae371 のAPI・DB・型・Tasksアーカイブを基準にする。今回は基盤/モデルのみでUI変更/Lazywebなし。後続でライブ/アーカイブ画面、確認と一括、2秒監視、取得所有権、復元待ちIDの詳細404照合、実ブラウザ/VMと永続化を実装・検証。202は受付に限り、完了時に項目が消える。本文原文を保持し、生の処理エラー/警告をUI文言として表示しない。

JSONを直接デコードし、正のInt64各ID・重複しない参照ID、進捗0〜100、正の形式版、非負Int64サイズ/残時間/件数を検証。必要な識別子/本文/状態/段階/日時を保持。エラー/警告は有無/件数に限定。任意/nullの参照ID・集計は空として扱い、tokens/skills/tools/findingsを投影（他の詳細集計はダッシュボード契約で扱う）。未知状態/形式は読めるが、UIは英日既知ラベルと安全な不明表示。復元/削除可否はブラウザ同様状態に従い形式検証はサーバーが行う。パッケージのホストパスは持たない。sha256が非空なら64桁16進。

一覧GETは200、ページ1以上・サイズ1〜100が要求と一致し、件数非負・行数はサイズ以内・ID重複なし。null一覧は空、欠落は不正。別DB照会間の追加/削除によりtotalと行数の一貫性を強制しない。検索4096UTF8byte/状態128byte、ページ計算はInt64内。URLQueryItemで値を符号化し、+を%2BにしてGoで空白にならないようにする。詳細GETは200と所有IDを確認。

単独保管POSTは202/同一task_id/archive_queued、復元POSTは202/同一id/restore_queued、削除DELETEは202/同一id/delete_queuedで本文なし。再試行は失敗3状態に対応する明示操作のみ。不一致/不正応答/送信後キャンセルは後続モデルで結果不明として扱う。詳細404をこの層だけで復元成功と推定しない。

一括は3経路へPOSTして202。継承順序で並べ替わるためIDの集合・件数・重複を照合し応答順を保持。成功はqueued=trueと正のarchive_id、失敗はfalseで生メッセージを保持しない。保管済み項目の応答archive_idは指定IDと一致し、ライブ成功の割当IDは重複不可。ライブIDは正規化/重複除去後に100件、保管IDは元配列100件判定後に重複除去する。応答4MiB/有限要求。受付は処理完了を証明しない。

大整数/FEFF/NFD、正常並べ替え/部分成功、件数境界、202/状態/所有者、正常形式の不一致、集計/形式/クエリ、上限、前後キャンセル、再試行選択、英日ラベルと可否（単独は継承ブロックを確認、一括はサーバー順序に委ねる）をTDD検証。レビュー・全体回帰・署名/翻訳後に反映。今回は実変更/VM/画面なしで全21機能/通信/カーネル/配布は未完了。

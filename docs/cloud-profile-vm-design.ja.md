# 隔離VMでのクラウド設定永続化

ビルド済みcloud1をCPU1のソースカーネル候補へ組み込む。検証済みのループバック限定イメージとinitを引き継ぎ、本体とinitのSHA-256を検査して読み取り専用システムディスクを再生成する。カーネルとinitramfsも検証済みのものを使う。NICとホスト共有は0。DEBUG専用試験では固定した本体ダイジェストと版を要求し、VMControllerで成果物を検証し、起動後のhealth応答で版を確認する。実際のSwift LLMServiceと本番プリセット初期化子からPostgreSQL設定APIを試す。

新規の権限0700の出力先と空の2 GiB状態ディスクを使用する。初回起動で未認証API拒否を確認し、使い捨て管理者を作る。独立した合成キーで非アクティブかつプール除外の4社設定を作り、公式URL・形式・マスク済みヒントを確認する。Geminiをキー空欄で編集し、同じディスクで正常停止・再起動する。通信資格情報を新しくし、同じ管理者パスワードでログインしてID、設定値、ヒントを照合する。両起動で会話とLLM記録件数を読み、停止後に隔離とログ内資格情報の不在を監査する。初回のみフォーマットの証拠を要求する。報告には安全な設定項目と判定を収める。

候補のダイジェスト／版／NIC／共有／CPUと、設定のURL・ヒント・重複・余分な行の異常を試験する。Releaseでは診断モードを拒否する。実行成功でCP1bの実設定保存の証拠を得る。次のCP2実機条件はツール履歴の保存と再起動後の再送。実クラウド通信、画面とブラウザの比較、カーネル／既定ゲスト昇格、リリースは別の受け入れ条件として扱う。

# 元データ保存modelの回帰防止

内部modelのチェックポイントであり保存UIの導入ではない。1c3b7a3でmodel／scopeの未実装REDを定義し、5a03c1fで寿命・実ファイルの4件が通過した。7e1b0c5では別バイト列に対して正常なレシートを返し、失敗なし・成功記録・誤ファイル公開の3アサーション失敗を再現。4123dd6で再入する開始判定と停止した所有者の試験を追加し、合計5失敗を再現した。非公開の一時ファイルと模擬転送／選択器を用い、クラウドや外部対象には接続していない。

5 Whys: 正常なレシートで別の元データを公開できた理由は要求メタデータと比較していなかったため。ファイル単体の整合性は書込側のmanifestを検査するだけなので、UI境界でも元のID／side／長さ／hashを維持する必要がある。開始が重なる理由は所有権を確保する前に可否callbackを実行していたためで、最終の検査には転送整合性だけでなく再入と現在の所有者も必要である。

Fishbone: IDはUTF8生バイト、詳細scopeは固定値。メタデータ・パネル・転送の前後と公開直前で所有権を確認する。外部callback前に開始を確保し、終了後も稼働／busy状態を再検査する。取消を終了まで待ち、遅延レシートを破棄し、清掃失敗は画面終了時でも区別する。観測通知によるstopは同期遷移が終わるまでキューに入れ、旧処理が終わるまで新処理を開始しない。既存認証・VM・ファイルの検査を維持する。

ID生バイト／side、パネル取消、未対応／別所有者、二重開始、遅延メタデータ・レシートの失効／取消／終了、別本文、開始判定の再入、終了所有者の試験を残す。root／ウィンドウ接続、model経由の実VM保存、UI／キーボード／VoiceOver／全21比較は単体試験とは別に未完。

e778df7でcallback前の開始確保、稼働／busy再検査、レシートstatus／長さ／SHAの要求manifestとの照合を追加し、対象8件が通過。レビューで両方の阻害指摘の解消を確認した。NFC／NFDの生バイト差と清掃失敗の専用表示も試験。実ウィンドウ／パネル／model経由の実VM受け入れは主張しない。

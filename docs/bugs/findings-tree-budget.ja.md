# F1 Findings資産ツリー件数の回帰

MUSUBIの5段階で固定DTO/クエリ/サーバーの確認、実際に失敗するネイティブ読取、誤った厳密上限の除去、重点/全回帰と固定ブラウザ計算の検証、ソース参照とRED/GREEN履歴・未達ゲートの保存を行う。

時系列:7871fba FindingRecord/サービス未実装のコンパイルRED、fd898ec 初期13件GREEN。60dc0e4 oracle未実装RED、d69da1b ハッシュ固定ブラウザ絞込み実行GREEN。レビューで正常JSONのサイズ超過・複合PATCHの自動再送なしを補強。さらにdb/finding_assets.go:597–616を確認すると、3000目標はendpoint、serviceの順で層を削除するだけで、root_domain/companyのツリーは超過し得る。e53b981は4MiB以内の有効な3001ルート応答を実際に試験し、ネイティブデコーダの拒否を再現した。ネイティブ同等性の不具合であり、ARTEXサーバーの障害や実VM受入の証拠にはしない。

5 Whys: 有効なツリーが失敗 → 3000件超過 → ソース定数を厳密保証と扱った → 間引きアルゴリズムまで追わなかった → 初期の拒否試験が推測した上限を補強した。根因はソースの努力目標を通信契約の不変条件に強めたこと。Fishbone: 定数と実装、間引かれないルートドメイン/企業、試験の拒否期待、独立した転送バイト上限、反復的な構造検証、未知種別とUnicode識別子。

修正はノード件数制限だけを除去。応答4MiB、UTF8キー一意、親の存在、循環/負件数の拒否、線形の反復検証を保持する。3001ルートとtruncated/dropped-kindsを受入れ、多ノード循環・重複グループ/タスク・正常JSONのサイズ超過は引き続き拒否。カーネル候補/既定VM/ブラウザ/利用者状態は変更しない。

関連仕様: 操作用finding_idはタスクのノードIDと異なる。継承/旧行は変更不可。task_id絞込みとtaskエンドポイントを区別。必須配列は明示的nullを許す。PATCHは逐次適用で、HTTP失敗の前に一部項目が適用され得る。サービスは自動再送せずエラーとし、後続の状態/UIでも不明結果を維持する。未知読取enumやCJK/FEFF/NFDはそのまま保持。状態/UI/実VM/参照/出力/通信/系譜/再検証/深掘りと全21受入は未達。

# エラー言語対応の調査 — L4a基盤

## 1. 再現

既存サービスは日本語の静的な`BackendAPIError.validation(String)`を作り、storeが失敗時点の`.localizedDescription`を保持します。Chat操作と異なり明示的なアプリ言語に追従できません。ソースから構造上の不足を確認した段階で、新たに英語の実画面でエラーを再現したとは主張しません。

## 2. 証拠収集

`ea39007`は未実装の`AppErrorText`／`BackendValidation`を3試験から初めて参照した意図したコンパイルRED。同じ3試験を`a3f7681`でGREENにしました。製品の16検証箇所はguard条件を保持し、理由を型へ移行。既知／一般HTTP、Keychain数値、添付、未知のエラーを検証。秘密・パスを含む未知のエラーも固定の一般文言だけを返します。

## 3. 原因分析

5 Whys：日本語のまま→サービスが表示済み文字列を渡す→理由がString→明示言語の共通表示境界がなかった→初期機能移植が全体言語要件に先行した。Fishbone：サービスの理由識別・storeの早期文字列化・カタログ同梱・明示localeの所有者・任意backend文言の安全性。Timeline：文字列／利用箇所調査→要件／設計／計画→意図した未実装API RED→理由型／表示GREEN→レビュー→全試験／coverage→署名同梱確認。

## 4. 修正

ネイティブ検証を閉じた16種類の`BackendValidation`へ移し、言語を明示する`AppErrorText`を追加。新規29項目（検証16＋通信／添付／fallback13）を日英カタログで管理。store移行中の互換性のため従来`LocalizedError.errorDescription`は明示的に日本語表示を維持。埋め込みはHTTP／Keychainの整数だけで、任意本文・パス・エラー詳細・ユーザー内容を翻訳／表示しません。backendのLLM未設定判定は従来の完全一致多言語allowlistを維持し、判定の拡大やネットワーク能力追加はありません。

## 5. 検証と再発防止

Swift243件（成功242・既存AX1件スキップ）、Python52件成功。AppErrorText行26/26・領域21/21。最終署名アプリのビルド／厳格署名検証成功、各言語29項目の同梱内容が元カタログに完全一致。読み取り専用レビューで具体的な問題なし。既存の互換エクスポーターと差分検査を維持します。

store／UIはまだ早期に日本語へ文字列化しています。エラー表示中の言語追従・実native／browser比較・runtimeエラー・R8全体は未完了。次はobservable storeに理由を保持し、viewのlocaleで表示し、フォーム／本文／添付を入れ替えず切り替わることを確認します。この基盤変更ではUI／browser／VM実行試験をしたとは主張しません。

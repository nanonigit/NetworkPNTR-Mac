# LLM通信の取消回帰

## 1. 発見・再現

合成通信で、取消済みの処理が送信されること、取消後の成功応答が返ること、4 MiB超の妥当なJSONが受理されることを再現した。RED08456c8は6件・39箇所のアサーション失敗。実キー、クラウド要求、ゲストへの書込は使用していない。

## 2. 証拠・時系列

既存試験は経路・DTOを扱い、取消を無視して返る通信を扱っていなかった。最初の試験コードはBackendAPIErrorがEquatableではないためコンパイル失敗した。パターン照合に修正後、本番コードを変えずに6件の挙動REDを確認した。共有境界の修正で6件が通り、LLM関連全22件も成功した。GREEN21e540aのコミット件名の37件は記載誤りであり、実際の関連試験は**22件**。

## 3. 根本原因

5 Whys：取消後に送信されたのはrawが無条件にsendしたため。遅延応答が返ったのはステータスしか確認していなかったため。注入可能な通信は取消に協力するとは限らず、下位層の挙動に依存していた。経路・形状試験に取消時の所有権を含めていなかった。Fishbone：コード＝await前後の確認欠落、通信＝取消協力は保証されない、試験＝敵対的な応答がない、工程＝有限JSONの前提をサービス自身が確認していない。UI・プロバイダ挙動を原因とする証拠はこの試験にはない。

## 4. 修正

送信前とawait直後、ステータス・本文の確認前に取消を確認する。要求・応答は4 MiB超を拒否し、ちょうど上限は両方向で試験する。公開API、経路、入力検証を維持し、再送処理は追加しない。

## 5. 検証・再発防止

11系統の送信前取消、不正JSON・エラーステータスより先に扱う送信後取消、遅延成功、保存・モデル取得・接続試験の要求超過、上下限の回帰試験を保持する。今回はサービス契約の証拠のみ。LLMStoreの所有権、書込結果不明時の確認・再開制御、閉じたエディタの処理所有権には別途の試験と復旧UIが必要。取消された送信済み書込は成立済みの可能性がある。ブラウザ／ネイティブ実画面操作とVMの受入試験は未完了。

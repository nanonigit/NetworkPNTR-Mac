# T17a 終了済みフィクスチャのスキーマ調査

MUSUBIの5段階で固定スキーマとレビュー証拠収集、ネットワークなし実PostgreSQLでの再現、カテゴリnkey修正、DB/ファイル一致と再投入拒否の検証、正規化した実証拠と再実行方針を保持した。初期の模擬子プロセス成功はコマンド境界だけでSQLの妥当性を証明しなかった。

固定db/schema.sqlのtask_categories.nkeyはNOT NULL UNIQUEで既定値がないが、投入はid/nameだけだった。完全なコンポーネントスキーマで旧32139e1を実行しnkey_not_null_violation=true・tasks_after_failure=0を確認した。ファイル書き込み前に拒否された。修正はサーバーの空白整理/小文字化と一致するASCII定数't17 archive category'を指定し、動的な正規化ライブラリを増やさない。

時系列:2c9a0b8のモジュールなしRED→境界7件成功→レビューでnkey欠落→コンポーネント準備は/sbin不足、その後別のEnsureLLMUsageTable初期化DDL不足で失敗し私的に保持（列不一致の証拠とはしない）→初期化を揃えて旧nkey不備を再現→公開RED証拠を原因分離済みのものへ更新→修正版で実投入/読み戻し/再投入拒否成功。履歴を書き換えず、元のブラウザ4コンテナを維持し、各実験の所有コンテナは削除した。

5Whys:トランザクション失敗→必須列NULL→可視カテゴリ項目だけをSQLへ転記→通常はサービスがnkeyを生成→模擬成功では実スキーマを実行しなかった。根本原因は手書き診断SQLが派生必須列を落とし、境界試験だけをSQL証拠としたこと。Fishboneはnkey/別DDL、手書きSQL、模擬終了コード、PATH、DB/ファイル非原子的処理、安全な拒否証拠と推定原因の区別。

固定スキーマとdb/llm_usage.goから抽出したDDL、通信なし/ホスト共有・ポート公開・特権なし、Linux/aarch64のUID1000で実行した。done・未停止・未キュー・モデルなしの2タスク、1カテゴリ、3ファイル計1056バイトが一致した。Unicode名とハッシュも一致し、保管/モデル/活動/使用/会話は0件。再実行は既存ファイルを拒否し、SQL直接再投入は既存行で拒否、読み戻しは不変だった。これはPostgreSQL部品の証拠でARTEX/VMの実保管操作ではない。SQLとファイルは非原子的で、失敗時は成功も自動再送もせず使い捨て実験の証拠として保持する。実ジョブと同じディスクの再起動はT17bで受け入れる。evidence/tasks/t17a-seed-sql-red.jsonとt17a-seed-sql-green.json参照。

# チャット状態と参照環境の境界調査

対象は新しい有限API・状態管理と開発者向け比較環境です。利用者のデータ消失やホストのサーバー変更は観測していません。今回は通信・状態管理・インフラの修正で、追加のLazyweb UI調査は対象外です。MUSUBI Bug Hunterの再現・原因分析・修正・検証・再発防止を適用しています。

## 5 Whys

新しいメッセージが消えるのは、古い停止済み応答が新しい送信の取得要求を消すためでした。選択中の会話と生存世代だけを調べており、同じ会話内の送信による鮮度変更を区別できませんでした。最初のテストは選択変更と送信失敗を別々に確認していました。再発防止として、古い差分の待機を送信成立の前後にまたがせるテストと、変更世代を導入し、通信枠を重ねず順番に再取得します。

停止後に再開したのは、送信が一覧更新のawait後に再確認せず差分取得したためです。一覧側は応答を破棄しましたが、呼び出し元は停止を認識しませんでした。停止は後の画面復帰のため選択を保持するので、選択の存在だけでは古い処理を続けてよい根拠になりません。依存する処理を始めるawaitの境界で元の生存世代とキャンセルを再確認します。

参照スクリプトがホストに通信するのは、トップレベルでHTTP処理を始め、docker execでの利用を前提にしたためです。ローカル実行やimportも可能で、loopbackの指す環境が変わります。最初のCLIテストは呼び出しの有無だけを確認していました。main限定実行と実行境界の確認、ホスト・マーカーなし・importのモック回帰テストを追加しました。

## Fishbone

並行処理：要求順序、変更世代、重複通信の抑制。ライフサイクル：データの保持と古い継続処理の無効化。API：runningは取得時点の情報で、その後の送信が含まれる保証ではありません。実行境界：loopbackの意味がホストとコンテナで変わり、説明文だけでは制限になりません。テスト：通信を意図的に待機・モックし、利用者のデータを触らず競合と境界を検証します。

## 再発防止と限界

追加テストは既存CIで実行します。変更世代とawait後の生存確認を保ち、最後の1000件が上限に達した応答はrunning=falseでも続けて取得します。成立した送信は更新失敗で未成立に戻さず、二重送信を防ぎます。編集中の下書きは保持します。参照fixtureのimportは通信せず、ホスト実行はHTTP前に失敗します。認証情報や生のバックエンドエラーは正規化した証拠に含めません。Pythonは標準ライブラリだけで、Swiftも外部依存がないためnpm/pipの依存監査は対象外です。

チャットUI、データ入り実ゲスト履歴、AI送信・実行中停止、添付・SSE、クラウド通信、クリーンMacでの配布の合格にはしません。chat-design.ja.mdとtasks.ja.mdの条件は未完了です。

## データ入りfixtureのlibpq接続境界

新しい履歴データ投入処理のレビューで、PGHOSTをloopbackに固定しても、継承したPGHOSTADDRが実接続先を上書きできることが分かりました。PGSERVICE/PGOPTIONSも意図しない接続・スキーマ設定を持ち込めます。同じ実装が既存のダッシュボード投入処理にもありました。RED 0f6e0b4ではpsqlをモックし、PGHOSTADDR/PGSERVICE/PGSERVICEFILE/PGOPTIONSを意図的に設定して、実DBに接続せず2件の失敗を再現しました。GREEN ac57d2fで両スクリプトから継承PG*を除去し、その後に固定接続情報を設定します。新しい投入処理の6テストはすべて成功しました。

5 Whys：DSNはloopbackでも子プロセスに別の接続先が残り、libpqがPGHOSTADDRを使うためでした。親の環境をそのままコピーし、テスト側は環境を空にしていたので見落としました。libpq用環境の除去と、悪意ある継承値の回帰テストで防止します。Fishboneは子プロセスの継承、libpq接続先の優先度、固定SQLのトランザクション範囲、環境変数の負のテストです。SQLは固定で、fixture外の活動・タスク・検出結果・資産がある場合はトランザクション内で拒否します。これは検証用処理の対策で、一般のクラウド・外向き通信を合格にするものではありません。

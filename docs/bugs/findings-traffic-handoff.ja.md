# 準備済みと送信済みの証跡書込を分ける

MUSUBIの流れで状態/サービス境界を確認し、busy変化時の同期キャンセル/停止で再現、明示したhandoff記録へ修正、保留応答と回帰試験を確認し日英記録を残した。開発中の状態層は当初9件を通ったが、executeが通信前に取消を拒否しても状態層が不明扱いする点を独立レビューで発見した。

5 Whys: 通信ゼロの取消が不明→executeの全失敗を送信後扱い→サービスの取消確認前にticket作成→busy準備を送信と同一視→開始済み/応答後の取消しか試験しなかった。特性要因は段階境界・observableの同期再入・試験時点。時系列は未実装REDdedfcb2→7/9件GREEN→レビュー→21439beで11件/5アサーションRED→handoffとticket由来busyへ修正→重点21件GREEN→修正の独立再レビューで阻害問題なし。

サービスは取消確認後、transport.send直前に内部callbackを呼ぶ。状態層はsession/activity/owner/ticket/activeを再照合してからhandedOffを記録する。それ以前の取消/同期停止は通信や不明状態を生まずnotStartedとなる。停止時の不明記録もhandoff後だけで、送信後の取消/失敗は不明のまま。busyはobservableな現ticketから算出し、別flagと古いcleanupの不整合を防ぐ。callbackは公開の任意操作能力ではなく、固定経路・上限・認証transportは変更しない。socketにbytesが届いた証明ではなく、transportへの引渡しを保守的な不明境界とする。

再発試験はwithObservationTrackingでbusy変化時に同期取消/停止する。停止/再開の終了待ち、reset後の新しい書込を古いcleanupから保護、正確な不明回の確認、読取で解除しない、バイトtotalと外部snapshot/選択の拒否も保持する。他機能の準備/handoff境界は別の追跡監査であり、この記録で修正済みとは主張しない。

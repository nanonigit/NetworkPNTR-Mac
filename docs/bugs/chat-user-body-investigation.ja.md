# 保存済みユーザー本文の調査

対象はA6の本文・送信済み添付メタデータ。要件→設計→タスク→実装の順に進め、MUSUBI Bug Hunterの再現・証拠収集・原因分析・修正・検証を適用した。

一覧APIはDetailを省略するためSummaryだけでは添付カードが消える。固定transcript.tsxのparserをハッシュ検証して実行し、モデル・所有権付き取得・読み取り専用カードをRED/GREENで追加。

a324333のRED名称は訂正する。BOM不一致はSwift hasPrefixの欠陥ではなく、このMacのJSONSerializationがオラクル文字列内の先頭BOMを取り除いたためだった。直接生成・JSONDecoderではUTF8先頭239を保持。本文と空白テストを型付きJSONDecoderへ変更しBOMのバイトを明示検証した。履歴は書き換えず、不正確なREDを製品不具合の再現として数えない。

レビューで、会話行だけの削除では所有セッションファイルが残り、seed後の例外で後始末が抜けることを発見。会話削除後に所有セッション全体を削除し、全IDで継続・外側catchでも認証済みクライアントで後始末するテストと修正を追加。参照multipartの64KiB境界が終端を含まなかった指摘もe9c42bfで再現しd287b3aで本文全体に適用した。

5 Whys: カード欠落→Summaryのみ表示→保存Detail未取得→入力欄の添付実装だけでは履歴を網羅できない→対応表に保存済み行の受け入れを明記する必要。BOM誤検出→fixtureがバイトを変更→動的デコーダの挙動未検証→JSON読込は透明という仮定→バイト検証不足。Fishbone: データ境界、非同期所有権、fixtureの変換・削除、multipart終端、重複UI IDと削除操作。Timeline: 固定ソース→モデルRED/GREEN→BOM訂正→取得所有権→UI→後始末修正→全試験→実VM/ブラウザ3ケース→後始末確認。

Swift220成功・AX1明示スキップ、Python49成功。parser/store行100%、store領域94.3%、user view行77.1%。外部CUAで3ケースの文字どおりの本文、54B/0B、重複カード2個、削除なしを両画面で確認。全般のUI合格、クラウド成功、長い履歴・総メモリ、VoiceOver、カーネル信頼性は主張しない。

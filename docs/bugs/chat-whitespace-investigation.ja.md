# チャット送信のUnicode差分調査

要件・設計はrequirements.mdとchat-advanced-design.mdを参照。今回は処理部分の修正でLazywebの対象外。UI比較はA5に残す。

## 再現・根拠

チェックサム固定のブラウザ送信処理は、空判定・送信・失敗時復元の前にinput.trim()を使う。Foundationの空白集合は異なり、BOMは本文として通り、NELとゼロ幅空白は除かれる。前後空白のある本文もMac版では除去せず送信・復元していた。固定ソースは変更せず、限定した送信oracleを4例から9例へ拡張。RED54a1e26で実行した3テストが13箇所で失敗し、GREENcc3e64bで同じ対象が成功した。追加例はBOMのみ、NEL、ゼロ幅空白、前後空白と添付、BOMと添付。APIと状態を制御したソース実行であり、描画UIや実プロバイダーの検証ではない。

## 原因分析

5 Whys: Foundationによる空判定で差分発生→ECMAScriptと集合が違う→参照仕様の代わりにプラットフォームの便利APIを使用→引用検索の互換処理を送信側で共有していない→従来例は普通の本文と空文字だけでUnicode・前後空白が不足。

Fishbone: 言語仕様、Service/Store/Workspaceの判定重複、元入力と送信本文の復元、例の不足。Timeline: 未完了の比較条件を確認→固定Unicode例を実行→RED記録→共有処理・送信スナップショット修正→GREEN→別レビュー→全テスト・カバレッジ・署名ビルド。

## 修正・再発防止

ChatTextへ既存の引用検索用ECMAScript空白処理を移す。Workspaceは会話作成前に判定。Storeは元UTF8で楽観的クリアの所有権を判定し、trim済み本文を送信・復元、新しい編集を守る。Serviceは空判定のみ共有し、直接渡された本文は変えない。引用検索の先頭のみ・前後の除去動作は維持。ホスト実行・ネットワーク境界の変更なし。

Swift193件（Core179・AppKit5・診断9）、Python45件成功。共有処理は行16/16・領域10/10・関数4/4を実行、LLVMの分岐カバレッジ報告なし。oracle再生成は一致し、変更ソースは実行前に拒否。別レビューで具体的な問題なし。cc3e64bから署名アプリを再ビルドし厳密署名検証、起動は行っていない。evidence/chat/unicode-send-verification.json参照。

未完了: ChatViewの送信ボタンには従来のFoundation・添付のみ送信の判定が残る。A5のUI固有テストとLazyweb参照で修正する。実プロバイダー、ファイル選択・カード・取消・アクセシビリティ、ソースカーネル起動安定性は未完了。Core成功ではこれらの条件を閉じない。

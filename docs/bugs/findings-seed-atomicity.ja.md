# Findings投入トランザクションの原子性

## 1. 観測・再現

F4aのPython・セキュリティレビューで、最後の条件検査前に6つのsetvalがあることを発見しました。単体REDeac81deで連番のトランザクション要件が失敗します。同じ旧ソースを使う独立したPostgreSQL16.15でCOMMIT直前にゼロ除算を起こすと、行は空へ戻りますが6連番が進んだままです。これが問題を切り分けた再現証拠であり、投入成功ではありません。

## 2. 調査

5 Whys: setvalはトランザクションで戻らない→固定ID後の自動採番へ使った→テーブルの保護が連番にも及ぶと扱った→以前のファイルを含む非原子的な検証パターンを流用→最後の失敗を起こす試験がなかった。Fishbone: SQLの性質、固定ID、再利用、巻き戻し観測の不足、準備スキーマの不足。Timeline: 未実装RED6dcad07→境界8件→レビュー→連番の単体RED→修正→旧/新の実SQL比較→証拠レビュー。

準備失敗も保持しています。最初はUID1000のユーザー登録がなくinitdb前に止まり、投入SQLは実行していません。次は実行時に別途作られるllm_recordsがなくLOCKで止まり、行・連番を変更していません。どちらも連番問題の証拠には使いません。最終検証ではユーザー登録だけを加えたキャッシュ由来の派生イメージと、固定schema.sql・llmUsageSchema・llmRecordsSchema/Migrateを使いました。ローカルUnixのDocker接続とDockerドライバーのビルダーを確認・固定し、ビルド処理と検証コンテナのネットワークを無効化しました。ARTEXは起動していません。上限付きstdin・書き出しでread-only/tmpfsのdocker cp既知失敗を避け、ログ取得失敗でも自分のコンテナを清掃します。

## 3. 修正

固定のALTER SEQUENCE … RESTART WITH max+1をトランザクション内で使います。standard_conforming_stringsも明示します。実行環境・診断フラグ・接続先・子環境の検査と、上限付きpsql呼出しを維持します。COMMIT前のSQL失敗では行と連番が戻ります。プロセス期限切れやコミット応答喪失は結果不明として扱い、成功証拠を出さず、自動再試行しません。

## 4. 検証

実際の旧ソースでは行が空、連番が8111/8111/8200/8203/9133/15190へ進みました。修正版は行が空で6連番とも[1,false]を維持しました。巻き戻しを明示検証した後の予定した投入では、全33検出結果、31ノードの正確なpayloadと旧項目15190、11完了タスク、継承1件、トリガー生成の関連33件を読み戻しました。mainとSQLの両再実行を投入前に拒否し、行・連番は不変です。プロファイル・活動・会話・利用・再試験・通信ジョブはなく、ARTEXプロセスもありません。元のブラウザ4コンテナは同じIDを保ち、自分のコンテナと派生タグは削除しました。証拠はevidence/findings/f4a-seed-sql-{red,green}.jsonです。

対象9件・Python95件成功、Swift578件中577件成功・既存AX1件スキップです。欠落行を含めるtraceで101/102行（99.02%）です。部品の実証記録レビューで残件はありません。ARTEXのAPI、VM、再起動、UIの同等性は未完了です。

## 5. 再発防止

固定IDを使う投入では、最後のSQLを意図的に失敗させ、行と連番を両方検査します。実行時DDL、トリガーの正確な関連、名前付きのゲストUIDも準備します。一般的なSQL失敗を目的の問題と誤認せず、psqlのモック成功をSQLの証拠にしません。失敗の状態・ログと同一公開HEADのCIを保持し、カーネル・UI・全機能の条件は別に扱います。

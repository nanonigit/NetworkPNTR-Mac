# クラウドのモデル一覧試験：上流の状態確認前に通信が終了する

[English](local-session-cloud-egress.md) | [日本語](local-session-cloud-egress.ja.md)

状態：再現済み、原因未確定、実通信の受け入れ条件は未完了。[検証記録](../../evidence/local-session/cloud-egress-regression.json)。

## 再現と対照試験

DEBUG版VMProbeをビルドし、仮想化権限付きで署名します。毎回、新しい専用ディレクトリを使います。修正済みでハッシュ固定したクラウド成果物に対して `VMProbe --cloud-live-models CLOUD_ARTIFACTS NEW_OUTPUT --local-session` を実行し、変更前の同梱ゲストには末尾フラグなしの形式を使って比較します。無効な固定テスト値で4社の決められたモデル一覧ルートだけを呼びます。実キー、推論、設定・会話の保存は使いません。

最初の自動接続試験では上流の状態を確認できませんでした。その後、要求・認証・通信の動作を変えずに観測情報を追加しました。変更前の対照版と自動接続版のどちらも、4社すべてでアプリ応答200/ok:false、`unexpected-eof`、上流状態未確認を記録しました。3回の試験はそれぞれ終了コード1で終了し、別々の結果を残しています。モデル取得が失敗しただけでは、外部APIへ到達した証拠になりません。

システムのcurlは、プロキシ環境変数なしでOpenAIから401を受信し、TLS1.2限定でも接続しました。本番C関数を直接呼ぶ最小診断では、DNSで確認したIPv4の2候補に接続しました。どちらも非同期接続待ち（EINPROGRESS）に入り、4秒の接続段階で期限切れになりました。TLSハンドシェイクやHTTP要求には進んでいません。調査範囲は狭まりましたが、ファイアウォール、VPN、OSの制御、通信実装のどれが原因かは確定していません。

## 原因をたどる質問

1. 試験が通らない理由：どのプロバイダーでも、上流からの認証拒否を確認できないためです。
2. アプリの拒否だけでは不十分な理由：外部HTTPヘッダーを受け取る前に、vsockや上流通信の切断をエラーとして返せるためです。
3. 共通経路を疑う理由：変更前の対照版にも、自動接続版と同じ現象があるためです。
4. より狭い失敗の証拠：システムのcurlでは接続しますが、本番C処理の診断はTLSより前に期限切れになります。
5. プロセスによる違いの理由：未確定です。Macのロック解除後の実際の観測と、回数を限定した診断で、通信許可と接続段階の時間制約を切り分けます。

合格させる目的だけで期限を延ばしたり、接続先・ホスト名・オフライン証明書の検証を弱めたり、プロキシへ迂回したり、自動認証が原因と決めたりしません。対照版の失敗も保持します。実画面・実通信は未完了のまま、署名済みVMで通過したデータ保持・認証試験と区別して記録します。

## 再発防止

診断には、上流の認証状態に加え、固定分類のエラー種別とアプリ側HTTP状態を残すようにしました。不明なエラーや秘密を含む文字列は、そのまま記録せず `unclassified` にする回帰試験があります。結果配列には、起動モード、実行ファイル・ソース・ゲストマニフェストのハッシュを対応させます。診断変更または確認済みの外部状態変化なしに、成功するまで再試行しません。

来歴情報の限界：最初の自動接続試験では、診断実行ファイルとソースのハッシュを記録していません。後の対照試験と観測情報を追加した候補試験には両方を記録しています。最初のゲストマニフェストと失敗終了は記録されていますが、欠けた実行ファイルのハッシュを後から推定して補いません。

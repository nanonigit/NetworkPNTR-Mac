# 通信候補API：5段階検証記録

## 1. 発見・再現

F5の完全な操作一覧には通信候補のページ取得と元通信プレビューが必要だが、型付きAPIがなかった。RED e33e7b6でCapturedTrafficService/Queryの欠落を確認。原文全体の保存も不足しており、プレビューで代用せず後続の必須条件として保持する。

## 2. 証拠・時系列

固定版server.goのgetTraffic/getTrafficExchange、dto.go、traffic.Page、ブラウザAPI・型・候補／ビューアを基準にした。最初のコンパイル済み7件で1箇所失敗し、Foundationのクエリ復号が先頭UTF8 BOMを消費していた。実際の要求は`host=%EF%BB%BFe%CC%81...`で正しく符号化されていた。復号文字列を正解値にせず、独立したパーセントバイト復号でFEFFとプラス記号を検証する形へ変更。修正後の契約8件と既存を含む関連29件が成功（67e9be8）。

## 3. 根本原因・再発防止分析

5 Whys：候補取得ができないのはネイティブの取得APIがなかったため。従来は紐付け済み証跡を扱い、ブラウザの候補追加は全体の通信索引を参照する。有限・認証済み経路としての型が不足し、画面の同等性を後続条件として管理していた。Fishbone：範囲＝紐付け済み／未選択、状態＝取得停止／索引なし、識別＝文字の正規化同値とバイトID、検証＝任意／null／部分メタデータ、試験＝BOMを変えるFoundationの復号。この合成試験はプロバイダやネットワークの実障害を示すものではない。

## 4. 修正

固定GETの候補・元通信を型付き有限JSONで追加し、クエリとIDの符号化、バイト識別、索引なしの明示的な形を扱う。取得停止中の履歴は保持する。要求とページ・件数を照合し、件数・長さの非負とIDの一意性を検証する。別SQLで読む総数・一致数の同時性は仮定しない。符号化後8192バイトの経路と4MiB応答、await前後の取消、200限定、安全なエラーを適用。記録URLに接続せず、元通信プレビューやblob参照を原文全体とは扱わない。

## 5. 検証・再発防止

不正／null／部分／取得停止中履歴、独立バイト復号、Unicode正規化同値のID、経路・本文の上限ちょうど／1バイト超、妥当な応答での状態分類、送信前後の取消を保持する。レビューで指摘された状態試験の不足は妥当なreq/respと型付きエラー確認で修正した。実バックエンド・プロバイダ・キー・ゲスト書込は使用していない。候補の所有状態、証跡UI全操作、全バイト保存、実ゲスト／ブラウザ／画面受入は必須の未完了条件。

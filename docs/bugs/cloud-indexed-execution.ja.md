# 番号付きツール実行と履歴再送の原因分析

## 再現と経過

固定ChatAgentを実HTTPプロバイダーとファイル履歴で動かし、別々のLinuxプロセスで検証した。初回ターンは一時ファイルの固定Readを1回行い、元の引数・ID・署名と実結果を模擬プロバイダーが照合する。初回終了後に一時ファイルを削除し、次のプロセスは同じ署名付き履歴を送り、ツール実行0件を要求する。

最初は日付リマインダーを利用者発言として数えていた。固定形式の日付通知を区別するよう試験を修正した。0920bceの実行時REDはComplete成功、Stream失敗。再送された履歴に正しい引数があっても、実Readはfile_path不足となった。1db2758で交互引数、終了不足、通信切断、長さ制限、キャンセルを再現し、1c2d095で組み立て済み履歴を番号付き実行の入力にした。

レビューで実行境界を追加した。c4209b5は壊れた引数とID欠落・重複の実行、およびツール通知コールバックからのキャンセル後のキュー投入を再現した。c48ac4eは全件検証と通知後のキャンセル判定を追加。3e8aae8は開始前／未対応引数、キャンセル済みキュー、次ターンへ切り替わった後のセマフォ待ちを再現し、4b4c242で対応する開始への結合、未対応引数拒否、元ターンの実行文脈の保持を実装した。harness単体の依存取得を要求した試験準備は、実アプリの固定モジュールグラフで実行することで解消した。GREEN前にimportと上流試験の明示的な文脈引数を補った。

## 5 Whys

1. Readの引数が不足したのは、署名イベントで実行バッファが確定したため。
2. 署名で確定したのは、引数以外のイベントをすべてツール終了と扱っていたため。
3. 再送履歴が正しかったのは、別の番号付き集約器を使用していたため。
4. 既存試験で残ったのは、プロバイダーと集約器を直接試験し、ChatAgentの実行経路を通っていなかったため。
5. 別プロセスで確かめる必要があるのは、JSON形式の検証だけでは実際の履歴読み戻しと再送が確認できないため。

## 経路別の対策と再発防止

形式と集約。番号付き引数は対応する呼び出しへ集約し、開始より早く届く断片も保持する。完成ブロックを履歴と実行で共有し、通知前に生JSON、ID、未対応引数を全件確認する。

実行寿命。キュー、セマフォ待ち、実際のツール呼び出しまで元ターンの実行文脈を使う。通知でキャンセルされたバッチはキュー投入0件。中断結果を発行済みの場合は遅い完了で上書きしない。通常の番号なしツールは従来の早期実行を維持する。

検証。両方式の別プロセス復元、固定URL、交互引数、途中終了、壊れたバッチ、通知キャンセル、待機と期限の回帰試験を維持する。次の実機条件は、通常チャットAPIと永続状態ディスクを使う専用VM再起動である。

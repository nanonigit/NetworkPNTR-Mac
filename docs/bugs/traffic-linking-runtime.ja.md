# 独立通信画面の実行証拠不足

## 再現と証拠

今回以前は新しいネイティブ統合が模擬通信テストを通っていたが、既存VM検証は検出結果側pickerのみ。新しいTrafficStore／候補サービス／TrafficBindingStoreが実backendで動くことは未証明だった。2c495b4で意図したhelper未実装のコンパイルRED、da7f3aeで5件GREEN。これは検証範囲の不足であり、backend障害の再現ではない。dfb2d7aで既存DEBUGの2回起動probeへ接続し、既存pickerが同じ通信を再度紐付けても正規化応答／版が完全一致することを必須化した。

新規非公開ディスクと変更していないCPU1候補で、実際の2回の起動停止、ソース／エージェント非活動／隔離監査、元データ出力、検出結果編集の応答を意図的に失わせた復旧、再起動保持比較が成功。独立通信側は25＋4件を選択し、ordinal3／4を紐付け、古い要求の再送を拒否し、一致する選択のみ解除。実際の紐付け版1は後続の同じ通信の紐付けでも1を維持し、ブラウザAPI比較用データ全体が一致した。ネイティブ画面／Root／入力操作は実行していない。

## 5 Whys

1. 独立画面の実動作が未証明だった理由：新API／状態を模擬通信だけで試していた。
2. 既存VM成功で足りない理由：別のCapturedTrafficPickerStoreを使っていた。
3. 同じに見える理由：紐付けendpointを共有する。
4. endpoint共有だけで足りない理由：ページ／設定／ホスト／候補取得、所有範囲、送信内容の組立は異なる。
5. 固定の実験を再利用する理由：独立ブラウザ比較、冪等性、永続化／非活動監査を保ったまま新経路を検証できる。実UI受入の代わりとはしない。

## FishboneとTimeline

範囲：新Core経路と既存pickerの違い。契約：通信25件、検出結果20件、正規ID、既定refs、単回要求。実行：使い捨て永続ディスク、CPU1候補、NIC／共有なし、ハッシュ証拠、協調停止2回。基準：固定ブラウザAPI、冪等応答の完全一致、元データ全バイト。順序：要件／設計→helper未実装RED→5件GREEN→読み取り専用レビュー→全回帰→実VM成功→リリースのDEBUG除外確認と検証記録。

## 再発防止

全体成功には独立通信helperの成功と既存picker応答との一致を必須化。fixtureの件数／順序／重複ID、誤ページ、候補9101の不在／読み取り専用、不完全／失敗応答を拒否し、自動再送しない。実行結果／バイナリー／ソース／profileのハッシュを保持し、UI受入はfalseで記録。複数ホスト削除、blob拡張、実ネイティブ／窓／入力／アクセシビリティ、既定カーネル昇格、リリース／4社／ハーネス全体は未完。実際に応答を失わせた編集はFindingTrafficStoreの試験であり、新TrafficBindingStoreの応答喪失復旧は今回も単体試験まで。

リリース確認の手順補足：最初の実行は必要な位置引数を省略し、最上位usageが返ったため期待usageのassertionに失敗。3つのダミー位置引数を渡すとリリース側サブコマンドガードに到達し終了2。検証手順の修正であり製品ガードの欠陥ではない。

## Canonical Unicode filename collision

Independent review found that Swift String equality/hash canonical equivalence merges NFC é.txt and NFD e+combining-acute.txt, while pinned chatupload.go uses guest filepath/os.Stat without normalization. The first implementation rejected the valid two-file envelope, shared Identifiable keys, accepted a path/name pair with different bytes, and could collapse restore/removal. Executed RED25c877a produced five failures across model/store tests. GREEN512d9c0 uses Data(path.utf8) identities, byte-exact name/path agreement and custom metadata equality, plus byte-based append/restore/removal. The original display/wire strings are never normalized. Thirty-six scoped tests passed at that checkpoint; review approved the fix.

5 Whys: distinct guest files collided -> Swift equality normalizes canonical equivalents -> native strings were used as filesystem keys -> display equality was assumed identical to Linux path identity -> fixtures lacked composed/decomposed pairs. Fishbone: language semantics, guest filesystem, model identity, collection keys, test fixtures. Timeline: initial nine new core cases -> independent review -> NFC/NFD runtime RED -> byte-identity GREEN -> source-derived oracle includes both names -> followup review.

## A4.2 operation completion and text transfer

An upload could finish its network/body work, append accepted metadata, then wait for a list refresh. Explicit cancellation and a replacement upload during that await left the old method returning true, because only lifetime/task cancellation was checked. RED2219e94 executes13 workspace cases with one failed stale-success assertion; GREENb0d16e6 rechecks operation UUID after the final await (45 scoped cases). Already accepted files/cards are not rolled back; the obsolete call cannot report success for the replacement or clear its busy state.

A target draft edited during upload prevented seed text from replacing it, but the source root was still cleared. REDc296b78 reproduces one lost-text assertion. GREEN7be783c requires byte-exact text to exist at the target before clearing an unchanged source revision (46 scoped cases). Both newer target text and the original root now survive. 5 Whys: source disappeared without transfer -> clearing depended only on source revision -> target seed was skipped for edits -> source/target checks were independent -> tests omitted a user opening the just-created target mid-upload. Fishbone: ownership, two-slot handoff, byte equality, asynchronous user input. Timeline: basic handoff GREEN -> controlled target edit RED -> transfer-confirmation GREEN -> read-only review approval. The stale-completion chain similarly came from an await added after the result guard; keep operation checks after all final awaits.

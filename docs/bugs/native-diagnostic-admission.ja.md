# 検証用起動の開始条件

状態：起動順序の回帰試験3件に成功。署名済みアプリは検証処理とVM起動まで進んだが、ゲストが認証前にパニックで停止した。

再現：署名済み開発版を `--native-diagnostics NEW_PRIVATE_DIRECTORY --native-review --no-llm-review` で起動すると、プロセスと画面は存在するが検証用ディレクトリもVMも作成されなかった。未ログインのAI接続画面では許可ボタンが正しく無効だった。

期待：アプリ起動とSwiftUIによる実行環境の受け渡しが揃った時に、指定した使い捨て領域で検証を一度だけ開始する。

ソースと順序試験が示す原因仮説：起動通知から固定時間後にweakな実行環境を一度だけ確認し、未設定なら終了していた。画面の準備が後になっても再度開始する契機がなかった。固定待機では所有者と準備完了を保証できない。

5 Whys：開始しなかったのは一度だけの参照時に実行環境がなかったため。画面と起動通知は別イベントなので、受け渡しは後になる場合がある。開始条件が起動通知だけだったため後続の契機がない。2つの準備条件を扱わず固定時間で順序を仮定していた。既存の計画・データ試験では通知順序を検証していなかった。要因はタイミング、weak参照、一度だけの開始管理の欠如、実署名起動の確認不足。

経過：CLI起動が待機したままになり、未ログイン画面を確認した。終了後にアプリの操作ハンドルで状態を読むと通常起動が再開したため、正常停止した。認証情報は入力していない。以降は終了済みアプリを観測せず、プロセス一覧で終了を確認する。

修正：DEBUG専用の開始管理で、起動通知と実行環境の受け渡しがどちらの順でも揃った時に一度だけ許可する。処理を予約する前に許可済みにし、既存ウインドウの表示を最大2秒待って既存の検証処理へ渡す。ディレクトリを指定しない通常起動の動作は維持し、失敗した試験を自動再実行しない。

検証：起動後の受け渡し、起動前の受け渡し、通常起動の3試験に成功。署名済み環境の起動、外部UIでの許可・キャンセル・失効、実MCP・VM参照と停止ログ監査は別ゲートであり、本修正だけで完了とは扱わない。

署名済み再起動では検証専用領域が作成され、画面描画とVM起動を確認した。ゲストはstate_zero_checkでPID1が0x0000000b終了し、kernel6.12.114-0-virtがパニックした。VMは停止し、生ログは非公開の検証領域に保持した。開始条件の修正は確認できたが、ゲスト安定性と認証後MCP操作の成功とは扱わない。[検証記録](../../evidence/mcp/native-diagnostic-admission.json)を参照。

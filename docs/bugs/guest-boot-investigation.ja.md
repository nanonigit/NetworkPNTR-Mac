# ゲスト起動異常の調査記録

調査中です。安定動作・製品完成の合格とはしていません。

## 観測した時系列

1. P2の署名済みCLIでは通常・強制再起動、保存、API比較に成功しました。成功した起動での機能確認であり、長時間の信頼性を示すものではありません。
2. 実.appの初回設定テストで、Alpine 6.12.114-r0のPostgreSQL起動中に fib_table_lookup のカーネルNULL参照が発生しました。ホストは異常を認識してVMを停止しました。利用者の認証情報やブラウザ版データは使っていません。
3. 別の実.appでは初期設定と本物のKeychain保存に成功し、再起動後の復元時にEAGAINが発生しました。非ブロッキングのsocketpairと遅延応答で再現し、読み書きの前に待機する処理で回帰検証しました。容量・時間の上限も維持します。
4. 固定したAlpine 6.18.58-r0と対応モジュールはCLI検証と、実.appの設定・ログイン・Keychain復元に一度成功しました。別のテストでは認証状態オブジェクトの生成をAPI確認完了と誤判定していました。診断側が認証確認の完了を待つように修正しました。
5. その後の6.18でも、空ディスク検査中に未定義命令・ページ参照異常が再現しました。カーネル更新だけで解決したとはしません。1 CPUでの比較も同じ検査でタイムアウトしたため元に戻しました。ソース側の標準カーネルは更新していません。
6. 初期RAM・モジュール・ルート切替の経路と、必要なドライバーを組み込んでOSディスクを直接起動する経路を比較します。既に導入されているDocker Desktop公式配布のGPL LinuxKit 6.12.76カーネルを診断だけに使用します。SHA-256は 35dc83e45a0cbf9a292469e902fd6a5f4db58c9ead47e69233b4197661795fc8。組み込み設定では初期RAMが無効で、block・ext4・vsockが組み込みのため、読み取り専用ディスクから直接起動します。アプリ利用時にDockerを呼ぶ構成ではありません。ソース・ライセンス確認なしの配布や、配布用ソースビルドの代わりにはしません。

## 原因の分析

5 Whys：初回の失敗はゲストカーネル異常です。以前の成功と両立するのは、同じ起動条件でも間欠的に再現し、単発の成功だけでは信頼性を示せないためです。認証復元の別の失敗は、タイムアウト設定が非ブロッキングのFDをブロッキングに変えないことを見落としていました。さらに診断側が状態生成と確認完了を混同していました。カーネル自体の根本原因は、異常箇所が一定せず、バージョン変更でも消えないため未確定です。

Fishboneの切り口は、ゲスト設定、初期RAM・モジュール・ルート切替、ブロックI/O・疎な空ディスク、vCPU、ホスト環境、アプリの通信・準備完了判定です。証拠なしにmacOS・ハードウェア・特定パッチを原因と断定しません。既存の上流報告は症状が異なり、参考情報にとどめます。

## 直接ルート起動での追加確認

NICを接続しなくてもLinuxKitは無効状態のトンネル機器を作成します。そのためloだけという検査を、物理デバイス0・有効な非ループバック機器0・外部経路0の明示検査に置き換えました。起動前と準備完了時に確認し、それぞれの違反と証拠欠落を拒否するテストを追加しました。Virtualization.framework側のNIC・共有0という条件は維持しています。

最初の一連の実行では初期設定と通常再起動に成功した後、強制停止からの復旧でARTEXが終了しました。停止後に揮発ログが失われたため終了原因は未確定です。秘密を含み得る生ログは表示せず、固定したエラー分類と数値の終了コードだけを記録する診断を追加しました。次の実行では強制停止後の復旧・不正ディスク拒否を含む4起動が成功しましたが、直前の失敗は解決扱いにしていません。

同じ直接ルートLinuxKit構成でも、署名済みアプリの初回起動で空ディスクを調べるPython処理中に`anon_vma_clone`／`__split_vma`／`munmap`のゲストパニックが再現しました。追加モジュールは読み込まれておらず、初期RAM・モジュール・ルート切替だけが原因という仮説では説明できません。この構成も採用していません。直接ルート＋1 vCPUの比較を追加していますが診断限定で、通常コードは2 vCPUのままです。ホストやハードウェアを原因と断定していません。

直接ルートLinuxKit＋1 vCPUでは、新しい保存環境から署名済みアプリの診断が3回連続で成功しました。計9起動で、実際の初期設定・ログイン・Keychain復元・ログアウト時の削除・起動中の正常停止を確認しています。これは一時的な1 vCPUビルドでの結果で、原因の確定や配布の安定性判定ではありません。ソース編集なしで再現できるよう、manifestで1または2 CPUを指定できる範囲制限を追加しました。既定値は2のままです。選んだmanifestをネイティブとCLIの両方で再検証してから採用を判断します。ソースからのカーネル構築と実操作・画面比較の条件は残ります。

終了診断から1 vCPUの強制停止後に`backend_exit_status=1`と`database_open,database_recovery`が得られました。DBプロセスの起動と、復旧後にアプリ用DBが利用可能になる時点のずれという、別の準備完了待ちの不具合です。秘密値とログを非公開のまま、アプリ用の権限とDBで`SELECT 1`が成功するまで上限付きで待ってからARTEXを起動します。修正後、選択した1 vCPU manifestで強制復旧3回を含むCLIの6起動、追加の実アプリ設定・Keychain・ログイン・起動中停止、ブラウザ版との5つのAPI比較が成功しました。正規化した証跡はevidence/native-authに保存しました。カーネル異常の根本原因と配布品質の合格は未解決です。

## 修復の合格条件

最終的な固定構成で、新規設定・本物のKeychain復元・誤パスワード・同意なし・ログアウト・再起動・起動中の停止を反復し、Oops・パニック・停止しない状態がないことを確認します。同じ構成でCLIの保存・不正ディスク・ブラウザ版API比較も再実行します。失敗記録を残し、実クリックと画面比較の未完了条件を隠しません。状態と秘密値はGit対象外とし、ホスト隔離を弱めたり、既存ディスクを自動フォーマットして合格させたりしません。

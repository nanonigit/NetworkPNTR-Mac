# クラウド中継用Linuxクライアントの検証

cloud5候補には、ホストCID 2のポート8790へ接続するLinuxクライアントを組み込んだ。明示的に有効にした場合、固定のプロバイダー操作をMac側と同じ形式に変換する。不正な接続先や中継への接続失敗では直接通信に切り替えない。ノンブロッキングのLinuxソケットを使い、応答を読み取る間は送信側も開いておく。キャンセルで接続を閉じる。[Linux VSOCKの資料](https://man7.org/linux/man-pages/man7/vsock.7.html)

隔離したパイプ試験では、Gemini要求のバイト列、応答の1バイトずつの受信、不正なヘッダーとフレーム、途中切断、キャンセルを確認した。既存のモデル一覧と実行経路も試験した。修正前のSDKは中継終端なしでもSSEのDONEを成功とし、応答ヘッダーを失うと同じPOSTを4回送った。修正後は成功時と429・503などのエラー時にも中継終端を検証し、結果不明のPOSTは1回の送信で止まる。タスクとワーカーの再試行判定でも結果不明を拒否する。記録ラッパーが完了の条件を保ち、途中で切れた割当量エラーを失敗として返すことも確認した。AnthropicとOpenAI Responsesのエラーイベントも、中継終端の確認後にプロバイダーのエラーとして扱う。

オフラインLinuxビルドは固定ブラウザのコミット、従来の管理用パッチ、プロバイダーのvsockパッチ、固定SDKの終端パッチ、新規クライアントを使う。入力と試験結果は[検証記録](../evidence/llm/cloud-egress-guest-verification.json)を参照。試験ではAF_VSOCKをパイプに差し替えた。署名済みVMでの実通信と有効化、実API、固定ブラウザ版との比較は後続の受入条件。ホストCIは未検証。

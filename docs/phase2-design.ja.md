# フェーズ2：設計と合格条件

元の全体ゴールを継続する。フェーズ1の実画面操作ツールによる確認は保留のまま残し、独立したゲスト/バックエンド基盤の実装を進める。画面やブラウザ機能の比較条件を省略しない。

## 実現する操作

- Macアプリから、VM内の固定コミットのARTEXとPostgreSQLへDocker不要で接続する。
- VMを停止/再起動しても管理者認証、LLM設定、検証データが専用ディスクに残る。
- 改変されたシステム、想定外の既存ディスク、認証のないVM通信を拒否する。異常なディスクを勝手に再フォーマットしない。

## 構成

固定したAlpine ARM64カーネル、小さな起動RAMディスク、読み取り専用ext4 OSイメージ、別の書き込み可能なext4データディスクを用いる。NICとホスト共有は作らない。DBは比較基準と同じPostgreSQL 16。ARTEXはUID 1000で動き、実行ファイルを変更できず、ゲスト内部のDBだけに接続する。JWT鍵はワークスペースの外に置く。

virtio-vsockの専用ポートから固定のゲスト127.0.0.1:8787だけへ転送する。ホストCIDと毎回生成する256ビット通信トークンを検証する。秘密値はechoを無効にした固定形式のシリアル初期設定で渡し、ログに出さない。Mac側はURLSession/SSE/WebSocket対応のためアプリ管理の127.0.0.1・ランダムポートの入口を利用できるが、ホストのファイル/シェル/RPCを提供しない。ARTEX自身の初期設定トークンと認証も維持する。この入口はアプリが自動管理する内部機構で、手動サーバーやブラウザUIを要求しない。

ゲスト作成時だけ固定した使い捨てLinuxビルドコンテナを使用できる。出荷するアプリの実行にはDockerを呼ばない。ビルド材料・バージョン・ハッシュ・上流コミットを記録し、アプリ起動時の自動ダウンロードはしない。

## テスト

T2.1 ディスク新規作成は排他的で本人だけが読み書き可能。既存の正常ディスクを保持し、サイズ相違/シンボリックリンクは変更せず拒否。
T2.2 実用ゲストはvsock 1・ディスク2（OSは読み取り専用）・NIC/共有0。フェーズ1構成は変わらない。
T2.3 初期設定トークンは改行・不正形式を拒否し、descriptionでも秘密値を表示しない。
T2.4 実VMでDB/ARTEXが起動。vsock経由でヘルス確認。通信トークン相違を拒否し、ARTEXの未認証API拒否も確認。
T2.5 同じ検証データのAPI操作結果をブラウザ基準と正規化して比較。使用中のブラウザDBをテストで書き換えない。
T2.6 通常再起動・強制停止後にも認証/JWT/設定/データを保持。異常な非空ディスクを初期化しない。
T2.7 改変や保存先の異常を可視化し、ログ/証跡にキーを含めない。実画面での機能比較は別ゲートとして残す。

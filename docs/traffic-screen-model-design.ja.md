# 通信履歴の表示所有権と読取スケジュール（TR3）

TR3–TR5の全要件を維持する。今回は状態／スケジュールの実装で配置変更はなく、実画面の前にはLazywebを使う。TrafficFilterDraftsとTrafficStoreを既存のAPI／backend挙動を変えずに接続する。

ウィンドウのrootが持つモデルでストアと揮発性の結果不明ゲートを画面往復にまたがって保持する。表示ごとのUUID leaseを発行する。beginは旧タスク／下書きを破棄し、ストアを停止／再開して一覧・hosts・settingsを読み取る。古いBinding setter、タイマー、disappearは取得時のleaseで検証する。stopは下書き・読取・選択・queryを消去し、認証resetはresetSessionも呼ぶ。永続／複数ウィンドウ共通の結果不明台帳は追加しない。

6欄それぞれに300msタスクと不変チケットを割り当てる。検索によるストア所有権の更新で別欄のタスクを取り消さない。適用時は現在のクエリーへ一欄を反映し、ストアを同期設定し、Observation通知後も表示を所有する場合だけ下書きコピーを採用する。通知中の新規編集／beginは拒否し、stop/resetは待機させresetを優先する。後処理中の通知から再起動／再resetさせない。同一原文は何もせず、適用条件が同じなら履歴ページ維持・再読取なし。即時操作は適用済みテキストを使い、詳細検索解除では該当4欄だけのタイマーを取り消す。ページ移動は隣接ページかつストアの最新読取ゲートで判定する。

初回／手動／条件変更の読取も表示所有権付きタスクにする。同一所有権の読取中は置換せず、条件変更ではコアの読取世代を更新して旧タスクをキャンセルし、キャンセル無視の通信完了を待たず新読取を始める。表示ごとの5秒ループはpage0かつコアが許可したときだけ読み取りを要求し、結果不明のackや変更操作は行わない。待機関数はMainActorで注入でき、製品ではTask.sleepの300ms／5sを使う。制御した試験はスケジュール／条件分岐の検証で、実経過時間の精度や画面操作の証明ではない。

先に別欄タイマーと所有権更新、古い／再入力／旧表示の通知、stop/reset再入、上限拒否後の未採用、即時操作／詳細解除、最新隣接ページ、page0定期更新／履歴の手動更新、確認中抑止、古い保留読取、結果不明保持と自動再送／ackなしを試験する。その後読取専用レビュー、全試験／カバレッジ、署名ビルドを行う。RootViewと実画面操作は後続段階で、対応表はpending、TR3は未完了のままにする。

# ネイティブ画面と実バックエンドの接続設計

P2・P3を進めます。前ターンは実ゲストの保存・認証・5つのAPI比較に成功し、f524c0dを公開してCIも通りました。全体の画面比較条件は維持します。

## 要件・画面の基準

固定した実バックエンドを.appに同梱し、アプリ起動時に専用VMを開始します。利用時にDocker・Python・ブラウザ・シェルコマンドを呼びません。保存先は専用の非公開Application Support領域で、ブラウザ版とは分離します。初期設定、ログイン、接続失敗と再試行、ログアウトを実装します。パスワードはSecureField、確認入力、ユーザー名ARTEX、行内エラーと処理中表示を使います。503や通信障害を未初期化とみなしてはいけません。

基準は固定コミットの web/src/app/(auth)/setup/page.tsx と login/page.tsx です。初期化確認、パスワード一致、長さ制限、利用条件チェックと8節の説明を引き継ぎます。ブラウザの最小長はJavaScriptのUTF-16長、サーバーはUnicodeスカラー数です。Mac版はサーバーと同じ8スカラー以上・UTF-8で72バイト以内とし、差分を記録します。設定トークンは管理するVMにアプリが内部で受け渡し、コンソールからのコピーを不要にします。秘密値は表示・ログ出力しません。ブラウザ版の認証情報は取り込みません。

Lazywebでは2026-10-22に `desktop login password settings` を検索し、Canva 242519、Frontegg 251323、Notion 241065を取得しました。返された説明を、安定したサイドバー・明示的なラベル・集中したフォームの補助資料に使います。スクリーンショットを実見したとは扱いません。SwiftUIのMac向けパターンでキーボード操作・配色・画面の状態管理を設計し、ARTEX側の操作とエラーを優先します。実装の承認用レポートは新設しません。

## 分担・通信・認証情報

ArtexCoreに有限長HTTP/JSONの境界、型付き認証API、認証状態、Keychain保存、アプリ用保存先と起動管理を分けます。VMControllerはVMとvsockを担当し、Linuxの準備完了と認証状態を区別します。選択中の画面はRootView、実行環境はアプリ全体が所有します。パスワードは入力画面だけで保持し、認証状態の変更・画面を閉じた時点で消去します。入力エラーではブラウザ版と同じく再入力を不要にします。JWTだけを専用Keychain項目に保存し、UserDefaultsやファイルには書きません。

まず認証済みvsock上で有限長JSON APIを接続します。Content-Length・切断終端・chunkedを上限付きで解析し、不正な形式を拒否します。SSE・WebSocket・バイナリー入出力・キャンセルの合格とはしません。全機能の移植というゴールは維持します。

## 検証項目

- A1：通常・chunked・末尾ヘッダー、途中切断・形式の曖昧さ・過大応答、ヘッダーとパスへの改行混入を検証。
- A2：状態取得失敗時は利用不可を表示。初回は設定、無効なJWTはログイン。DB障害で保存済み認証情報を消さない。
- A3：不一致・長さ・UTF-8上限・同意なしではAPIを呼ばない。実エンドポイント・固定ユーザー名・JWTだけの保存・ログアウト消去を確認。
- A4：Keychain失敗を成功にしない。保護APIで確認できたJWTだけを復元。単体検証ではテスト用APIとメモリ保存先、実アプリでは本物のVMと専用の一時Keychain項目を使う。
- A5：署名済み.appがDockerを呼ばず実VMを起動し、製品用の接続処理で認証・保持を検証。内部診断はプログラムによる証跡であり、外部からの実クリックや画面比較の代用とはしない。

## 直接ルート起動の診断構成とネットワーク証拠

manifestの任意項目`bootMode: rootDisk`で、必要なドライバーを内蔵したカーネルを読み取り専用OSディスクから起動し、初期RAMディスクを使わない構成を検証します。未知の値やOSディスク欠落は拒否します。調査中は通常のAlpine構築手順を変更しません。インストール済みLinuxKitカーネルはローカルの診断材料に限り、配布依存にしません。ゲスト内の物理NIC0・有効な非ループバック機器0・非ループバック経路0をサービス起動前と準備完了時に検査し、無効な仮想機器も記録します。VM側のNIC・共有0条件は維持します。

作業順は起動形式と拒否テスト、実機起動・保存・異常時の記録、ネイティブ設定・Keychain・ログイン・停止の反復、固定ブラウザ版とのAPI比較です。実操作・画面比較、再現可能なソースビルドとライセンス配布条件は別途残します。ARTEX終了時は決められた分類と終了コードのみを表示し、生ログを出しません。

manifestの`cpuCount`は1または2だけを認め、既定値は2です。読み込みとVM構成の両方で制限し、診断には実際の設定値を記録します。ソースを編集せずCPU条件を比較でき、無制限のリソース指定は認めません。

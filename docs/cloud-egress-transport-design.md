# Direct transport for cloud egress

Connect a nonblocking TCP socket directly to the admitted numeric destination. Verify the actual socket peer before TLS and again before sending any provider bytes. Use a fresh connection per request. The worker does not resolve hostnames, evaluate proxy configuration, or follow redirects.

The Swift entry point pairs a generated CloudEgressRequest with a destination admitted for the same hostname. A worker owns the TCP socket and SecureTransport context. The caller can cancel from another thread. Bound TLS setup and the entire exchange with monotonic time, check cancellation while waiting and inside the TLS I/O callbacks, and close the socket on every exit. Deliver raw response chunks to a bounded sink without buffering the whole response. The vsock layer will validate HTTP response framing and own listener admission, a combined DNS and exchange deadline, and VM lifetime.

Exercise a real loopback TLS server with generated test trust, mismatched and untrusted certificates, a held response, a streaming response, cap enforcement and a configured proxy sentinel. Verify the production Swift entry rejects mismatched routes before starting any socket. Keep the default guest listener disabled pending the signed-VM acceptance phase.

SecureTransport pauses the TLS 1.2 handshake before server trust evaluation. Resume only after the fixed HTTPS name and chain pass Security framework validation with network certificate fetching disabled and locally cached revocation data allowed. A handshake that does not report the authentication break fails closed. The API is deprecated and limited to TLS 1.2. Keep its use inside this transport target and include all four providers in acceptance. See [Apple's SecureTransport documentation](https://developer.apple.com/documentation/security/secure-transport) and [server-authentication break](https://developer.apple.com/documentation/security/sslsessionoption/breakonserverauth).

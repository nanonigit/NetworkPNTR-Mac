# エージェントのトリガー

## 要件

固定ブラウザ版と同じカスタムエージェント用のルールと実行方針を扱う。定期実行、
脆弱性の発見、目標達成、タスクのタイムアウト、ツール呼び出し、タスク作成を
組み合わせられる。条件ごとのメッセージ、ツールの絞り込み、有効状態を保持する。

## 設計

既存の認証付き一覧・追加・更新・削除APIを使う。IDで更新・削除する前に、
選択したエージェントの最新一覧で所有を確認する。応答と再取得の両方で結果を確認し、
更新を自動再送しない。IDはInt64で保持し、旧データのnullツール一覧は空として扱う。
実行方針の更新は該当する3項目だけを送信し、読み戻す。画面操作とスケジュール実行は
ネイティブ画面の段階で受け入れを確認する。

## 試験

全条件の送信形式、別エージェントのID、不整合な応答、削除済みの行、他の設定の保持を
確認する。固定ブラウザ版のAPIと管理VMで、無効なルールを追加・編集・削除する。
無効なルールを使い、エージェントの起動を伴わずに保存を検証する。

固定版のAPIと署名済みVMで、全6条件を持つ無効なルールを追加・編集・削除できた。
VMでは再起動後に編集済みルールと実行方針を読み戻し、検証ルールを削除して
元の方針に戻した。2回の起動とも仮想NIC・ホスト共有なしで正常停止した。
Swiftテストは1,096件が合格し、既存の1件がスキップされた。

ネイティブ画面は固定ブラウザ版に合わせ、実行方針、条件、保存済みルールを分ける。
LazywebのDripとProductboardを参考に、編集中の内容と保存済みの行を区別する。
保存は明示的に行い、削除は確認する。変更に失敗した場合は再取得してから操作する。
新規作成時も有効・無効を選べる。

再処理されなかった。一方、

タイムアウトは再送せず、更新時点で実行中の古いタスクは今後の通知対象に残す。

### Mac版ゲストのタイムアウト通知修正

処理済みのタイムアウトをタスクIDごとに記録する。初回のスキーマ更新で、その時点で
すでにタイムアウトしているタスクを登録する。タスク表に残るアーカイブ済みの行も
対象とする。更新時に実行中の古いタスクは、その後タイムアウトした際に対象となる。
ポーリングは未処理の有効な行を一意キーで原子的に取得し、全ルール無効時にも行う。
他のイベントのポーリング条件は維持する。有効・無効の判定はポーリング時に行うため、
次のポーリングより先に再有効化すると、無効中に発生した通知も届く場合がある。
通常の再起動による再通知は抑えるが、取得後にサーバーが停止したりチャットエージェントが
利用できなかったりすると、会話への受け渡しが失われうる。
移行の再実行、順序の逆転、同時取得、全ルール無効、固定ブラウザ版との比較を
ゲスト切り替え前に検証する。

署名済みのcloud8候補では、遅れて発生したタイムアウトまで固定版と同じ順序で投入した。
小さいIDのタスクでReporter会話が1件完了し、次のポーリング間隔でも追加の会話は
発生しなかった。別の使い捨てPostgreSQL 16で、移行時の既存データ、移行の再実行、
同時取得を検証した。初回の試験は新規ディスクで行った。既存ディスクでの更新は後述する。
全ルール無効の試験結果は後述する。実画面比較は配布前の確認項目として残る。
[修正の検証記録](../evidence/agents/trigger-scheduler-timeout-repair.json)

更新試験ではcloud7で検証専用ディスクを作り、協調停止後に同じディスクでcloud8を
起動する。既存セッションと会話IDの維持、認証なしの会話取得が拒否されることを確認する。
旧版停止前に合成タイムアウト1件を論理削除する。通常のポーリングは削除済みの行を
対象外とするため、その行の処理済み登録はスキーマ移行によってのみ行われる。
新版で移行マーカーと合成3件すべての登録を確認し、両起動の隔離監査を行う。
ディスクの初期化は初回起動時にだけ発生することを確認する。

署名したDEBUG診断を固定cloud7とcloud8成果物で実行する。
`VMProbe --cloud-vsock CLOUD7 NEW_PRIVATE_OUTPUT --timeout-upgrade CLOUD8`。
出力先は新規ディレクトリを指定する。診断が専用ディスクを作成する。
署名済みの更新試験はMac実機で通過した。両マニフェストのハッシュと
停止結果は修正の検証記録に記載した。

全ルール無効の試験では、既存のカスタムエージェントのルールを一時的に無効化し、
過去分のタイムアウトを投入する前と、その処理済み登録を確認した時点で、有効ルールが
0件であることを確認した。登録を確認してから試験用ルールを有効化した。修正版VMでは
後から対象になったタイムアウトだけが会話を完了し、変更したルールも復元された。
固定ブラウザ版では、有効化後に過去分が実行された。検証対象はDB上のルール状態であり、
スケジューラーがメモリ内に保持したルール一覧は計測していない。先行試行ではゲスト
起動中にカーネルパニックが1回発生し、最終試行は隔離と協調停止の監査を通過した。

### 実時間でのタスク期限

通常のタスク作成APIで8秒の期限を設定する。Plannerには接続できないループバック専用の
プロファイルを使い、合成目標を未達成の状態に保つ。エンジンが記録した開始・期限・完了を
読み取り、期限が初回実行の8秒後であることを確認する。エンジンがUnix秒単位で期限を
比較するため、完了時刻には1秒の許容幅を設けた。Reporterには模擬ストリーミングを使い、
該当タスクの会話が1件完了することを確認する。最終Plannerがエラーになる経路を対象とし、
最終Plannerが正常応答して目標達成と判定するケースは別に検証する。

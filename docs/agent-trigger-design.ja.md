# エージェントのトリガー

## 要件

固定ブラウザ版と同じカスタムエージェント用のルールと実行方針を扱う。定期実行、
脆弱性の発見、目標達成、タスクのタイムアウト、ツール呼び出し、タスク作成を
組み合わせられる。条件ごとのメッセージ、ツールの絞り込み、有効状態を保持する。

## 設計

既存の認証付き一覧・追加・更新・削除APIを使う。IDで更新・削除する前に、
選択したエージェントの最新一覧で所有を確認する。応答と再取得の両方で結果を確認し、
更新を自動再送しない。IDはInt64で保持し、旧データのnullツール一覧は空として扱う。
実行方針の更新は該当する3項目だけを送信し、読み戻す。画面操作とスケジュール実行は
ネイティブ画面の段階で受け入れを確認する。

## 試験

全条件の送信形式、別エージェントのID、不整合な応答、削除済みの行、他の設定の保持を
確認する。固定ブラウザ版のAPIと管理VMで、無効なルールを追加・編集・削除する。
無効なルールを使い、エージェントの起動を伴わずに保存を検証する。

固定版のAPIと署名済みVMで、全6条件を持つ無効なルールを追加・編集・削除できた。
VMでは再起動後に編集済みルールと実行方針を読み戻し、検証ルールを削除して
元の方針に戻した。2回の起動とも仮想NIC・ホスト共有なしで正常停止した。
Swiftテストは1,096件が合格し、既存の1件がスキップされた。
[検証記録](../evidence/agents/trigger-service.json)

ネイティブ画面は固定ブラウザ版に合わせ、実行方針、条件、保存済みルールを分ける。
LazywebのDripとProductboardを参考に、編集中の内容と保存済みの行を区別する。
保存は明示的に行い、削除は確認する。変更に失敗した場合は再取得してから操作する。
新規作成時も有効・無効を選べる。

カスタムエージェントの詳細にトリガータブを追加した。ルールと実行方針は、
固定ブラウザ版と同じ6条件と設定値を扱う。有効・無効を変更する際は、固定APIが
要求するルール全体を送る前に最新版を取得する。他の項目の保持を含め、
Swiftテストは1,097件が合格し、既存の1件がスキップされた。
Macとブラウザの実画面比較は未完了。定期実行の発火試験では模擬プロバイダーを使い、
生成された会話と最終発火時刻を確認する。固定版のスケジューラが生成する
定期実行のタイトルとメッセージには中国語が含まれる。

署名済みのローカル配布プレビューにトリガータブと英語・日本語のリソースを同梱した。
署名済み管理VMと固定ブラウザ版の使い捨てバックエンドで、Reporterの定期ルールを試験した。
無効のままスケジューラの周期をまたいでも発火せず、有効化すると模擬プロバイダーを使う
新規会話が1件完了し、最終発火時刻が記録された。試験ルールは削除した。
VMは仮想NICとホスト共有なしで正常停止した。他の5種類の発火と実画面の比較は未完了。
[定期実行の検証記録](../evidence/agents/trigger-scheduler-interval.json)

タスク作成の試験では、無効時にタスクを作り、スケジューラの周期をまたいでから
ルールを有効にした。両バックエンドとも過去のタスクを再処理せず、新規タスクでは
そのIDに対応するReporterの会話が1件完了した。タスクの初期処理にはループバック専用の
プロファイルを、Reporterには模擬プロバイダーを使った。試験後にルールを削除し、
署名済みVMは仮想NIC・ホスト共有なしで正常停止した。
[タスク作成の検証記録](../evidence/agents/trigger-scheduler-task-creation.json)

脆弱性の発見トリガーは、使い捨てのタスクに固定の合成レコードを2件投入して試験した。
無効時のレコードは有効化後に再処理されず、新規レコードでは対応するタスクIDの
Reporter会話が1件完了した。固定ブラウザ版のバックエンドと専用VMで同じ結果を得た。
VMでは元のルールを復元して正常停止した。発見の記録後からモデルへの受け渡しまでを
確認した試験である。
[脆弱性の発見の検証記録](../evidence/agents/trigger-scheduler-finding.json)

目標達成には、発見トリガーと同じ検証ハーネスを使った。ルールの無効時に投入した
達成済みの目標は有効化後も再処理されなかった。2件目の合成イベントでは、対応する
タスクIDのReporter会話が1件完了した。専用VMと固定バックエンドの結果は一致した。
VMは元のルールを復元し、仮想NIC・ホスト共有なしで正常停止した。
目標が達成済みになった後の発火と会話実行を確認した試験である。
[目標達成の検証記録](../evidence/agents/trigger-scheduler-goal.json)

ツール呼び出しトリガーは専用VMと固定ブラウザ版のバックエンドで同じ結果だった。
過去の完了記録、対象外ツールの完了記録、対象ツールの結果がまだない呼び出しは
発火しなかった。対象ツールの結果を追加すると、対応するタスクIDと入出力を含む
Reporter会話が1件完了した。合成ログを使い、検証ルールを削除してVMを停止した。
[ツール呼び出しの検証記録](../evidence/agents/trigger-scheduler-tool.json)

タスクのタイムアウトは、専用VMと固定ブラウザ版で3件の状態遷移を投入して比較した。
別のルールだけが有効な間にタイムアウトしたタスクは、対象ルールを有効化した後も
再処理されなかった。一方、
それより先に作成され、有効化後にタイムアウトしたタスクの通知も抜けた。
IDがより大きい新規タスクではReporter会話が1件完了した。固定版は
`last_timeout_id` より大きいタスクIDだけを検索する。IDは作成順なので、古いタスクが
後からタイムアウトすると検索対象から外れる。署名済みVMは検証ルールを削除して
正常停止した。今回はタイムアウト状態の記録後の通知を検証した。時間経過による
タイムアウト判定と実画面は別途確認する。
[タイムアウトの検証記録](../evidence/agents/trigger-scheduler-timeout.json)

修正ではタスクの作成順とタイムアウトの発生順を区別し、再起動をまたぐ場合のルール
無効期間の扱いを定義する。固定版は全ルール無効時にポーリングを省略するため、その
ケースは別途試験する。修正版ゲストへの切り替え前に、古いタスクが遅れてタイムアウトしても
通知が1件だけ発生し、無効期間の通知が再送されないことを確認する。更新時点より前の
タイムアウトは再送せず、更新時点で実行中の古いタスクは今後の通知対象に残す。

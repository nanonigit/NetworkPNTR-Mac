# Traffic-to-finding binding state (TR3)

Full target remains browser LinkTrafficDialog: byte-identity flow selection across pages,250ms paged finding search(page1,size20), inherited/no-handle rows disabled, frozen selected flow IDs and finding handle, successful bind clears only the matching selection, EN/JA native dialog and real VM/browser comparisons. This checkpoint adds only the core action lifecycle before UI integration; it does not replace the full target with a service demo. Lazyweb is out of scope for this state-only step; it remains required before dialog layout.

Reuse FindingTrafficService's fixed GET/POST routes and prepared request validation. A TrafficBindingStore selects a mutable FindingRecord and unique literal source IDs, reads a fresh evidence summary, then binds default supporting/empty-note refs. Node IDs never substitute for canonical finding handles. Validate ID/body bounds before publication. Each selection creates an owner and request UUID; submitting consumes that request so delayed callbacks cannot replay it. Freeze encoded bytes before busy publication. Confirm only a verified response containing every selected source identity; POST's unchanged version is valid for idempotent already-bound refs. Missing/normalized identities become unknown, not success.

One outstanding write persists through stop/reset until settlement. Scoped stop/reentry/reset priority, generation-owned reads, immutable tickets and post-busy-release validation follow the standalone Traffic store's guarded boundaries. Stop/reset scrubs target/source/summary/receipt/error data. Unknown markers and a private canonical finding handle+minimum version survive for explicit recovery; no titles, packets, source list or credentials are retained in that settled ledger. The private handle is memory-only and never exposed or persisted; only an explicit authenticated recovery read may reveal a fresh server summary for it. This is neither a durable nor cross-window/process journal.

Post-dispatch failure/caller cancellation/departure conservatively marks unknown; dispatch is a logical transport invocation, not socket-byte proof. No automatic retry or acknowledgment. Recovery requires the exact current owner/revision, an available matching fresh summary with version>=the prepared baseline and no in-flight operation, then explicit acknowledgment. Ack rotates the request UUID; it never posts. Missing/inaccessible recovery data keeps writes blocked. A view/root must retain this store, include its busy/unknown gate in both bind and traffic deletion eligibility, and clear parent flow selection only after a current confirmed outcome and matching selection revision. Those parent/UI contracts remain following work.
